# E3 着手前のレビュー

M5〜M7、E1、E2 (PR #8〜#14) を読んだ時点でのまとめ。前回は [pre_M5_review.md](pre_M5_review.md)。
方向性は [EMU_GPU_PLAN.md](EMU_GPU_PLAN.md)、本線は [GPU_PLAN.md](GPU_PLAN.md)。

## 全体への所感

- M5 から E2 まで、3 通り比較 (参照モデル / Verilator / 実機) を崩さずに進んでいる
- ハーネスが効いている。frame_crc のフレーム先頭判定 (VBLANK 明けのクロックに画素があると落とす) と、
  sdram_ctrl の rd_sample をバースト途中で取り込む問題は、どちらも実機では表に出ない種類の不具合で、
  Verilator のシナリオと `memtest` の掃引がなければ後で化けて出ていた
- PSDA の位相調整と、selftest が「余裕 2 段未満で fail」を記録する形になったので、pre_M5_review の 1 番は閉じた
- 資源: LUT4 5,955 (約 29%) は E5 までの見積もり (6,000〜8,000) の範囲内。**BSRAM は 39/46 で残り 7**。予想どおり BSRAM が先に詰まる

## 1. E3 の前に: レイヤごとのラインバッファをやめ、順位タグ付きの作業ラインを 1 本にする (E2.5)

### 問題

- E2 はタイルのパスが `tbuf` (偶奇 2 個の BSRAM) に書き、ビットマップのパスでそれを上に重ねている
- このまま E3 でスプライトのラインバッファ (偶奇 2 個) と OAM (1 個)、E4 で 2 面目の `tbuf` (2 個) を足すと 44/46 で、入るか入らないかになる
- E4 でメガドラの優先度 (高優先スプライト > 高優先 A > 高優先 B > 低優先スプライト > 低優先 A > 低優先 B > 背景) を
  レイヤごとのバッファで再現しようとすると、合成器の比較が複雑になる

### 提案

- 作業ラインの各ピクセルに `{色 16bit, 順位 3bit}` を持たせる (今の `tbuf` の偶奇 2 個をそのまま使う)
- 各パスは「不透明で、かつ順位が格納済みより高いときだけ書く」。読み出しを 1 クロック先行させた 読み‐比較‐書き で 1 ピクセル 1 クロック
- パスの順位: B (タイルの優先度ビットで 0 か 3) → A (1 か 4) → スプライト (2 か 5)。ビットマップ レイヤと背景色はレジスタで順位を決める
- これで E3/E4 を足しても BSRAM は OAM の 1 個しか増えず、40/46 で止まる
- ライン予算: 2 面 + スプライト + ビットマップで約 1,700 クロック (予算 4,000)
- 完了条件: E2 のシナリオがすべて同じ CRC のまま通る (構造変更だけを安全に確かめる)

E3 でスプライト専用のバッファを足してからでは二度手間になるので、E3 の前に切り出す。

## 2. E3 (スプライト) で決めておくこと

- スプライトの形: 先頭タイル + 幅・高さ (1〜4 タイル) + 反転 + パレット + 優先度
- **セルの並び順のフラグを 1 bit 持たせる。** タイルの並び順が機種で違う
  (メガドラは列優先で縦に連続、SNES は 16 タイル幅の表から行優先、PC エンジンは独自)。翻訳層が楽になる
- 1 ラインの上限は「スプライト数」ではなく **ピクセル数** (メガドラは 320) で数える。実機の挙動に近く、`max_line_cycles` の上限とも対応が取れる
- X は負を許す符号付きにして、BLIT と同じクリップの規則を流用する
- VRAM の読み出しポートはタイルのパスとスプライトのパスが順番に使うので、1 つで足りる (GPU の `VRAM_WRITE` は書き込み側のポート)
- OAM の走査 (128 エントリ、1 クロック 1 つ) はラインの合成の先頭で行い、当たったものだけライン内リストに積む
- 完了条件 (EMU_GPU_PLAN.md のまま): 上限ちょうど・超過・画面端のシナリオがモデル = Verilator = 実機

## 3. M8 は E2 で置き換え、代わりに `STRETCH_BLIT`

### M8 を閉じる理由

- M8 の 3 つのうち、大きい `BLIT` は M7 (SDRAM の行をまたぐソースまで) で済み、
  毎フレームの CRC は `m7_frames` と E1 の印付きフレームで仕組みが揃い、スクロールのシナリオは `e2_tiles` の 2 番が実質それ
- 残る `DRAW_TILEMAP` はタイルレイヤの劣化版。毎フレーム 38,400 ワード (約 0.7ms) を SDRAM に書くのに対し、
  タイルレイヤは SDRAM を使わずに同じ絵を出し、ラスタースクロールもできる
- `DRAW_TILEMAP` にしかできないのは RGB565 の直接色のタイルくらいで、それも 8x8 の `BLIT` 1,200 回 (約 3ms、HSTX なら 24KiB/フレーム) で同じ。
  本当に必要ならタイルレイヤに 8bpp/16bpp モードを足す方が筋がよい
- GPU_PLAN.md の M8 の行と `DRAW_TILEMAP` の表は消さず、「E2 のタイルレイヤで不要になった。opcode は予約」と書き残す
  (後でエージェントが計画を読んで実装し始めるのを防ぐ)

### `STRETCH_BLIT` (`0x0E`) — GUI 向け。エミュレータには不要

- M7 の BLIT (ソースの行をバーストで読んでラインバッファに置き、宛先の行をバーストで書く) に DDA を 2 つ足すだけ
  - 宛先の行ごとに `sy_acc += sy_step` でソースの行を選ぶ。宛先のピクセルごとに `sx_acc += sx_step` でラインバッファから拾う
  - 透過色・クリップ・DQM による端の処理は BLIT のものがそのまま効く。左右反転は累算器の初期値をソースの右端にして step を負にする
- **割り算はホストにやらせる。** 引数に `{dh, dw}` と `{sy_step, sx_step}` (16.16 固定小数点) の両方を渡し、ハードは累算するだけ
- **丸め方を 1 つ決めて文書に書く** (参照モデルと一致させるため)。累算器の初期値は step/2 (ピクセルの中心でサンプル) が、縮小のときに偏りが出ない
- **1 ピクセル 1 クロック** (1 ワード 2 クロック)。BLIT の 2 ピクセル/クロックは、拡大縮小では 1 ワードの 2 ピクセルが同じ偶数番目のソースを指しうるので使えない。
  全画面でも 240 行 x 約 700 クロック ≈ 2.7ms
- 縦に拡大するときは同じソース行を何度も読むので、「前の行と同じソース行なら読み直さない」を足す
- 補間はしない (最近傍だけ)。バイリニアはソース 2 行と乗算器 4 つが要り、GUI 用途には割に合わない
- 引数が 6 ワードになるので、BLIT の高速パスを壊さないよう別 opcode にする
- 資源: BSRAM は増えない (BLIT のラインバッファを使う)。LUT は 300〜500 程度
- 完了条件: 拡大・縮小・非整数倍・反転・透過・クリップ・画面外のシナリオでモデル = Verilator = 実機。
  全画面の `STRETCH_BLIT` 中も表示の読み出し待ちが UNDERFLOW を出さない

## 4. 順番

E2.5 (順位タグ付きの作業ライン) → E3 → M9 (タイルレイヤ + スプライト + 図形で 60fps、ホストのスクリプトだけで動く) → E4。
M9 を E3 の前にやると、背景はタイルレイヤ・スプライトは BLIT という過渡的な組み合わせになり、E3 で書き直しになる。
M9 は E5 の翻訳層を書く前の、ホスト側のコマンドの組み立て方の予行にもなる。`STRETCH_BLIT` は M9 の前後どちらでもよい。
