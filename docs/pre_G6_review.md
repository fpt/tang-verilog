# G6 着手前のレビュー

G4、G5、配置に強くする PR (#39)、テクスチャのキャッシュ 64 行 + かたまりの並び (#42)、ハーネス v2 の基板 (#40〜#43) を読んだ時点でのまとめ。
前回は [pre_G4_review.md](pre_G4_review.md)。計画は [GPU3D_PLAN.md](GPU3D_PLAN.md)。

## 全体への所感

- 4 つの場面 (logo の金の環境マップ、tunnel の霧、room の床への映り込み、city の窓と街灯の加算) が、20K LUT の FPGA とオープンなツールだけで出ていて、
  しかも `g5_scenes` が **モデル = Verilator = 実機**。見た目と検証可能性が両立している
- **#39 が転換点**。G4・G5 の配置が通っていたのは運だったと見抜き、`gowin_arch_gen.py` から「nextpnr が見ないのは真のデュアルポート BSRAM の B ポートの番地だけ」と死角を 1 点に絞り、
  yosys が勝手に RAM を DP にして番地に論理を入れる落とし穴 (RTL を見ても分からない) を `scripts/bsram_check.py` で**合成結果を静的に検査してビルドで止める**形にした。
  pre_G4_review の「死角を叩く BIST」より強く、安い。複数の種で全シナリオが合う (既定と種 7 で 2 回ずつ、種 3 で 1 回)、という完了条件はこの検査があって初めて言える
- テクスチャのキャッシュは、`texcache_sim.py` で数えてから設計を決めた典型。64 行 + 4x4 のかたまりで tunnel 70% → 98%、1 フレーム 846K → 490K クロック、見積もりどおり
- 資源 (3D GPU、nextpnr): LUT4 14,000 (67%、ALU 込み)、ALU 4,050、DFF 6,102 (6,956 から減った。配置の上限 約 7,000 に余裕)、BSRAM 17 / 46、MULT18X18 4。
  VDP のビットストリームは変わらず (LUT4 10,331、BSRAM 44)

|---|---|---|---|---|
| logo | 239 | 369K → 約 170 | 33.3fps (1 フレーム 3,007 ワード) | リンク |
| tunnel | 237 | 490K → 約 128 | 46.6fps | リンク + 転送と描画の重なり |
| room | 190 | 573K → 約 110 | 49.8fps | 同上 |
| city | 348 | 1,280K → 約 49 | 30.7fps (GPU が 20ms > 16.7ms なので `SWAP` が 1 回待つ) | **GPU** |

## 2. 次に効くこと (順に)

### 2.1 走査線ごとの左右の端 (外接矩形の空振りを消す)

- 今はタイル ∩ 外接矩形の全ピクセルでエッジ関数を評価している。各走査線の左右の端を 3 本の辺から直接求め (符号が変わる x を 1 行に 1 回計算)、その区間だけ走査する
- ロジックは小さい (1 行に 1 回の除算なし。辺の係数から x の範囲を求めるのは乗算 1 回か、前の行の端を増分で追う)
- city の 1 フレームは 1,280K クロック → 正確な端で約 890K、安い版で約 990K (60Hz の 1 フレームは 1,050K)。どちらでも GPU だけなら 60fps に届く見込み (安い版はぎりぎり)
- **まず安い版** (除算なし、論理が小さい)。足りなければ正確な端。あわせて、行ごとの固定費 (`T_DRAIN` / `T_DRAIN2` / `T_ROW` の約 3 クロック、city で 30,691 行 = 約 90K) も削る

### 2.2 ISP / TSP の分離 (重ね描きのテクスチャを消す)

- G3 では「テクセルの取り出しが描いたピクセルの 1.11 倍だから分けない」と判断した。city (重ね描き 3 倍、テクスチャあり) はその判断を覆す測定になった
- **ただし今の場面は Z を送っていない** (奥から手前に並べるだけ)。見えるピクセルを決めるには Z が要るので、ISP / TSP に分けても今の場面には効かない。
  ホストが Z を送る (1 三角形 +3 ワード、city でリンクが約 3 割増える) 版の場面を作ってから見積もる。テクスチャの外れの待ち (city で 319K) のうち、隠れるピクセルの分しか減らない
- 2.1 のあとで city がまだ足りなければ。タグのバッファ (BSRAM 1 個) と、タイルのパスを 2 周にする制御。被覆ピクセルの走査は 2 倍になるが、テクスチャの外れの待ちは見えるピクセルの分だけになる
- `texcache_sim.py` を「見えるピクセルだけ」で数え直せば、分ける前に効き目が見積もれる

### 2.3 2 px / クロック

- 上の 2 つのあと、まだ足りなければ。DDA と比較器が 2 組になるので LUT と DFF が増える。今の余裕 (LUT 67%、DFF 6,100) なら入るが、配置の種の検証を全部やり直す

## 3. リンクはハーネス v2 (HSTX) で消える

- 37MB/s (620KB/フレーム) なら、logo の 3,007 ワード (12KB) は 1 フレームの 2% で、全部の場面が「GPU だけの数字と 60 の小さい方」になる
- FIFO の深さ (2,048 ワード、512 ワードより BSRAM +3) は転送と描画の重なりのためにあるので、リンクが速くなれば 512 に戻して BSRAM を取り戻してもよい (測ってから)
- Pico 2 が来たら最初にやる。E5a の受信側 (IDDR x4、非同期 FIFO、パケットの CRC) は Verilator で先に作れる。HSTX が使えないときの代わり (PIO で SDR 4 レーン) にも対応できるよう、受信をパラメータ化しておく
- #43 の基板の確認 (ネット、HSTX の等長) は済んでいるので、残りは実装と配線テスト

## 4. G6 の判断に新しい選択肢: 再コンフィグで切り替える

- VDP と 3D を同時に使うゲームはない。Tang Nano 20K には RECONFIG_N (ピン 9) があり、GW2A はフラッシュに複数のビットストリームを置いて切り替える multi-boot に対応している。
  **ゲームごとに FPGA を再コンフィグする**形なら、同居させる必要がない (再コンフィグは 100ms 程度)
- 要確認: apicula / openFPGALoader で multi-boot のイメージが書けるか、ホストから RECONFIG_N を叩く配線 (ハーネス v2 に 1 本足すか、BL616 経由か)
- これが使えると、G6 の判断は「どちらか片方が入るか」になる:

| | 3D 単体 (LUT 14,000、BSRAM 17) | VDP 単体 (LUT 10,300、BSRAM 44) | 同居 (約 24,300、61) |
|---|---|---|---|
| Tang Nano 20K (20,736 / 46) | ◯ (今) | ◯ (今) | ✗ |
| ECP5-25F (24,288 / 56) | ◯ 余裕 | ◯ | ✗ (LUT も BSRAM も溢れる) |
| ECP5-45F / 85F | ◯ | ◯ | ◯ |

- 同居を諦めて切り替えるなら、Tang Nano 20K のままでも完成形に行ける。ECP5-25F に移る理由は「ピン数」と「DSP とタイミングモデルの信頼性」だけになる

## 5. 上流に出すもの

- `ADB` (DP BSRAM の B ポートの番地) の登録先の間違いは **nextpnr** (`himbaechel/uarch/gowin/gowin_arch_gen.py`、YosysHQ/nextpnr) にある (apicula ではない)。
  まとめと報告の下書きは [NEXTPNR_GOWIN_TIMING.md](NEXTPNR_GOWIN_TIMING.md)。直れば `bsram_check.py` の違反 0 を保つ手間がなくなる
- 同じ文書の 2 章: 配線のあとの解析が、長い組み合わせの経路を (FF で受けても) 落とすことを最小の再現で見た (配置のあと約 12MHz の経路が、配線のあとは消える)。
  原因は未確認。それまでは配置のあとの Max frequency も見る (3D GPU は配置のあと 66.9MHz、配線のあと 105.8MHz)
- DSP の経路の欠落も nextpnr。`-nolutram` (LUT RAM が実機で壊れる) は apicula (書き出し) か nextpnr かを最小の再現で切り分けてから出す

## 6. 細かいこと

- `g1_fps` が 60.0 → 58.1fps (タイルのパスの固定費が数クロック増えた) は許容範囲だが、2.1 で固定費をまた増やさないように、シーンの外の `TRI` の経路は計測を残す
- `capture_min` 0 のシナリオ (`g3_tex` check 4) は「正しさは CRC で見る」の明示なので、docs のキャプチャの死角の行に足しておく
- ハーネス v2 で VSYNC を DDC_CLK (52) に移し HEARTBEAT を落としたのは、レベルシフタ付きの線を FPGA 出力に使う形。配線テストで波形を 1 回見ておく (2.2k の 5V プルアップと 2N7002 の負荷)。
  **HARNESS2.md は「2.2k プルアップ (3.3V)」と書いていて食い違う**。Tang Nano 20K の回路図で確かめてどちらかを直す
  (レベルシフタがあれば、Low を出すとき 5V 側の 2.2k から MOSFET 越しに約 2.3mA 流れ込む。`DRIVE=8` なら問題ないが書いておく)
