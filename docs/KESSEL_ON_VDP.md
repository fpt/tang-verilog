# Kessel を VDP で動かす

[rs-kessel](https://github.com/fpt/rs-kessel) (16bit スタック VM のファンタジーコンソール) を、RP2350 + Tang Nano 20K の VDP で動かすための設計メモ。
方針は「エンジンをハードに寄せる」。VDP 側に足すものと、Kessel 側で変えるものを分けて書く。
VDP の現状は [EMU_GPU_PLAN.md](EMU_GPU_PLAN.md) (E4 まで)、[GPU_PLAN.md](GPU_PLAN.md) (M9 まで) と、この文書の K1〜K5a。
コマンドやデータ形式の正確な定義は [SPECIFICATION.md](SPECIFICATION.md)。

## 0. 結論

- Kessel のスクリーンのポート群 (`0x10`〜`0x2c`, `0x70`〜`0x78`, `0xa0`〜`0xe2`) は、`x` `y` `colour` を置いてから `draw` を書く形なので、**そのままコマンド列**。
  ここを GPU バックエンドの境界にし、ソフトラスタライザは参照モデルとして残す (tang-verilog の 3 通り比較と同じ構図)
- VDP 側で一番大きいのは **8bpp インデックスのビットマップレイヤ**。これがないと `pal()` の意味 (描き直さずに色が変わる) が壊れる
- Kessel 側で一番大きいのは **描画の深さを 3 段に決めること** (面 < 即時描画 < ハードスプライト)。それ以外の API はほぼそのまま
- ライティングは諦めなくてよい。8x8 ピクセルのセルのライトマップを合成器の最後に掛ける
- 塗り速度は心配ない: VDP の BLIT は 63MHz で全画面 0.6ms 程度。制約はリンクの帯域と、レイヤの順の固定さ

## 1. Kessel の描画モデルと VDP の対応

| Kessel | 意味 | VDP での実現 | 状態 |
|---|---|---|---|
| フレームバッファ 8bpp、256 色パレット | 全部インデックス | **8bpp ビットマップレイヤ** (2 章) | ✅ K1 |
| `pal(i,r,g,b)` | パレット書き換え、描き直しなし | `PAL_WRITE` (RGB888 → 565 の丸めを 1 つに決める) | あり |
| `cls(c)` | 全面塗り | `CLEAR` (8bpp 版) | ✅ K1 |
| `pset` `hline` `vline` `rect` | 即時描画 | `POINT` `DRAW_LINE` `FILL_RECT` (8bpp 版) | ✅ K1 |
| `clip()` 相当、Square240 の額縁 | 描く範囲 | `CLIP` (`0x07`、M6 からある) | あり |
| `spr(id,x,y,flags)` 4bpp + `sprbank` | 即時描画 | **BLIT4** (4bpp ソース + バンク → 8bpp 宛先、透過 = 0) | ✅ K1 |
| `sprn` (w x h タイル、`id + row*w + col`) | 多タイル | BLIT4 をタイルごとに、またはハードスプライトのセル順 2 | ✅ K2 (4 章) |
| `spr_scaled` (8.8 固定、最近傍) | 拡大縮小 | `STRETCH_BLIT` (4bpp ソース) | ✅ K3 |
| `sspr(addr,…)` | メモリ上の生タイル | SDRAM に置いて BLIT4 | — |
| `map(tx,ty,sx,sy,tw,th)` + `camera` | タイルブロックの即時描画 | **面 A / B** (スクロール = `tx*8 - sx + camera`)。3 回目以降は BLIT4 | あり |
| `mget/mset/fget/fset` | VM の RAM | VM 側のまま。ダーティ行だけ `VRAM_WRITE` で面のマップへ | — |
| `text` `number` (3x5 フォント) | 即時描画 | フォントをタイルの形式で SDRAM に置いて BLIT4 | — |
| `ambient` `light` `light_rect` `shadow_rect` | ピクセル単位の RGB 乗算 | **セル単位のライトマップ** (5 章) | ✅ K4 |
| Square240 / Landscape320 / Portrait320 | 3 画面 | 320x240 そのまま / 左右に額縁 / 限定対応 (6 章) | — |
| フレームベクタ、200,000 命令/フレーム | 毎フレームの呼び出し | RP2350 で VM を回し、`WAIT_VBLANK` で区切る | — |
| 音 (イベントログ + シンセ) | ホスト側 | RP2350 のもう片方のコアでシンセ、PCM を HSTX で送って I2S へ | 要追加 (FPGA の I2S 出力) |

色モデル: ビットマップの 8bpp インデックス = パレット 0..255。BLIT4 は `bank*16 + nibble` (バンク 4bit) なので同じ 0..255 に届く。
`nibble 0 = 透過` も VDP と同じ。

**ハードスプライトも 256 色に届く (K2)**。前からのモードのパレットの番号は `{SPR_BANK[2:0], エントリのパレット (2bit), nibble}` で、
1 つのスプライトから使えるのは SPR_BANK の 64 色 (Kessel のバンク 4 つ分) だけ。`SPR_BANK[3]` = 1 にすると、
**OAM の word1 `[19:16]` のスプライトごとのバンク 4bit** で `{0, bank, nibble}` (0..255) になる。`sprbank` の値をそのまま OAM に書けばよい。

## 2. VDP 側: 8bpp ビットマップレイヤ

- 1 ピクセル 1 バイト、4 ピクセル / ワード。1 ライン 320 バイト = 80 ワード (1KiB の行配置はそのまま、400px でも入る)
- 書き込みの端とマスクは DQM (バイトマスク) なので、今の 2 ピクセル/ワードより素直
- `REG_WRITE` に `BITMAP_FMT` (0 = RGB565、1 = 8bpp) を足し、ビットマップのパスでパレットを引く (合成器の 512 エントリのうち 0..255)。
  透過の色は `BITMAP_KEY` の下位 8bit (インデックス、既定 0)。透過そのものの有効・無効は今と同じ `LAYER_CTRL` bit1
- **透過とインデックス 0**: Kessel では `cls(0)` や `rect(…, 0)` は不透明の色 0。透過を常に有効にすると、それが下の面やライトの背景色に化ける。規則:
  - そのフレームに面 (`map`) がなければ **透過を切る**。`cls(c)` はビットマップへの `CLEAR c` で、色 0 も普通に塗れる
  - 面があるフレームだけ透過を入れる。`cls(c)` は背景色レジスタ + `CLEAR` (透過色) になり、透過色のインデックスで描いたものは透ける。
    ホストはそのフレームで使われていないインデックスを透過色に選べる (`BITMAP_KEY` を変えるだけ)。全部使われていれば 0 にして、観測レコードに出す
- **クリップ矩形は今の `CLIP` (`0x07`)** をそのまま使う。`FILL_RECT` `DRAW_LINE` `POINT` `BLIT` (8bpp・4bpp のソースも) に効き、`CLEAR` には効かない。
  Square240 の額縁と Kessel の `clip()` 相当に使う
- コマンドの 8bpp 版: `CLEAR` `FILL_RECT` `DRAW_LINE` `POINT` は色が 8bit (コマンドの色の `[7:0]`) になるだけ。`BLIT` は 8bpp ソース → 8bpp 宛先 (透過色は `[7:0]`)。
  **BLIT4** は `BLIT` のフラグ bit3: 4bpp ソース + バンク (`[11:8]`) → 8bpp 宛先、透過のときは値 0 を書き飛ばす。
  4bpp のソースの並びはタイルの 1 行と同じ (1 ワードに 8 ピクセル、ピクセル i は `[31-4i -: 4]`) なので、タイルのシートを SDRAM に置けばタイル t は
  `src = base + 8t`、stride 1 の 8x8 の BLIT4 になる。ソースは SDRAM だけ (VRAM は合成器の中にあり、描画エンジンからは読めない)
- `STRETCH_BLIT` も 4bpp ソース版を主にする (Kessel の `spr_scaled` はシートのタイルを拡大する)
- 塗り速度の目安 (63MHz): 全画面 `CLEAR` 約 20k クロック (0.3ms)、8x8 の BLIT4 1 個 約 100〜150 クロック、200 個で 0.5ms。全画面 `STRETCH_BLIT` 1.7ms (8bpp、実機。K3 の結果)
- 資源: ビットマップのパスにパレット引きの段が 1 つ増えるだけ。BSRAM は増えない

## 3. Kessel 側: 描画の深さを 3 段にする

Kessel は全部がペインターズオーダー。VDP はレイヤの順が固定。次の規則に変える。

```
  面 (map)             ← 最下層。面 B (1 回目) / 面 A (2 回目)。カメラがそのままスクロール
  即時描画 (ビットマップ) ← cls / pset / rect / hline / vline / spr / sprn / spr_scaled / text。互いの順は保たれる
  ハードスプライト (任意)  ← 最上層 (優先度ビットでビットマップの下にもできる)。予算付き
```

- **`map()` は同じフレームに描いたものの下に出る**。1 フレームに 2 回までが面 (B → A の順)。3 回目以降と、`tw x th` が小さい断片的な呼び出しは BLIT4 に落とす。
  これが Kessel 側の唯一の意味の変更。`cls` の色の扱いは 2 章の透過の規則
- **面は折り返して画面全体を覆う**が、`map()` は矩形 1 つ。ホストは面のマップの、その `map()` が描かない部分をタイル 0 (透明) で埋める
  (前のフレームとの差分だけ `VRAM_WRITE`)。面の大きさは 32 / 64 / 128 セル (最大 1024px) なので、それより大きい Kessel のマップは
  メガドラのゲームと同じく、カメラの移動で画面に入る列・行だけを書き換えて回す。面は画面より広く取る (横 64 セル以上、縦 32 セル以上) ので、
  画面に入る範囲が 1 枚の面に収まる限り折り返しは見えない
- **`spr()` は既定で BLIT4 のまま**。描画順を厳密に守る (`outrun` の道路の上の車、`tetris` の盤の上の `spr_scaled`) にはこれが正しく、
  塗り速度に余裕があるので性能上の理由でハードスプライトにする必要はない
- **ハードスプライトは opt-in の別 API** (`actor(id, x, y, flags)` のような名前)。128 個まで、1 ラインに 320px まで、OAM の順で手前が決まる。
  使う理由は「毎フレーム BLIT を送らなくてよい (リンクの帯域)」と「動く物が多いゲーム」。
  予算の超過は VM の観測レコード (`vm_run_frame` の戻り) に出す。Kessel の「エージェントに機械の限界を見せる」思想と合う
- **今のレジスタでの順位**: `bitmap_rank = 6`。ビットマップは面のすべて (B は 1/4、A は 2/5) より上、
  高優先のスプライト (6) はビットマップより上 (ビットマップのパスは「書かれている順位より大きい」ときだけ書くので、同じ 6 ならスプライトが勝つ)、
  低優先のスプライト (3) はビットマップの下 (高優先の面の下にもなる)。RTL の変更はいらない
- HUD は即時描画なので、ハードスプライトの下になる。HUD の上に出したい物は優先度を低くして描く (= ビットマップの下)。文書に 1 行

## 4. スプライトシートの並び

- Kessel の `sprn` は `id + row*w + col` (幅 w で行優先)。VDP のセル順は 0 = 列優先 (メガドラ)、1 = 16 タイル幅の表 (SNES)
- VDP に **セル順 2 = 行優先・ストライド w** を足した (K2)。タイル = `先頭 + row*w + col`。シートの id 体系が変わらず、
  `sprn(id, x, y, w, h, flags)` の生の形がそのまま OAM のエントリになる (`先頭 = id`、`w`、`h`、反転、`sprbank` → word1 `[19:16]`)
- セル順は OAM の word0 の `{[10], [30]}` (0 列優先、1 SNES、2 行優先)
- VDP の 1〜4 x 1〜4 タイルの上限は Kessel 側にも書く (それより大きい `sprn` は BLIT4 に落ちる)

## 5. ライティング: セル単位のライトマップ

Kessel の光はピクセル単位の RGB 乗算 (64 = 等倍、255 = 4 倍)。これを解像度だけ落として VDP に載せる。

- **ライトマップ**: 8x8 ピクセルのセル、320x240 で 40x30 = 1,200 セル。RGB 各 6bit (0..63 = 0〜4 倍、16 = 等倍) を 18bit に詰めて BSRAM 2 個 (400px なら 50x30)
- **合成器の最後**で、作業ラインの RGB565 にセルの値を掛ける (18x18 乗算器 3 個、1 ピクセル 1 クロックのまま)。セルの境目が気になれば横だけ線形補間 (乗算器 +3)
- **ホストがセル解像度で計算する**: `ambient` はセル全部を埋める、`light` は `1 - d²/r²` をセル中心で評価、`shadow_rect` はセル単位のレイウォーク。
  1,200 セルなら RP2350 で 1 フレーム数十 µs。毎フレーム `LIGHT_WRITE` で 3.6KB (HSTX なら無視できる、SPI 15MHz でも 1 フレームの 1/8)
- Kessel 側の変更は「光の解像度は 8px、`radius` はセル単位」だけ。`rogue` `sokoban` の見た目はほぼ保て、`dnb` の `light_rect` (UI の枠) はセルに揃えれば完全に同じ
- ライトマップを使わない ROM は乗算の段を素通り (レジスタで無効)。資源は LUT 500〜800、乗算器 3〜6、BSRAM 2 (40 → 42 / 46)
- ライトマップはラインごとに切れる (`LAYER_CTRL` bit5 を `WAIT_LINE` で切り替える) ので、HUD の行だけ光なしにできる (`light_rect` の代わりに使える)
- **BSRAM が足りなくなったときの逃げ道**: セルを 10 x 8 ピクセル (32 x 30 = 960 セル) にすれば、18bit x 1,024 の BSRAM 1 個に収まる (2 → 1)。
  ホストの計算は変わらず、`LIGHT_WRITE` のセルの番号が `cy * 40 + cx` から `cy * 32 + cx` になるだけ。今 (44 / 46) はやらない

## 6. 画面モード

| Kessel | VDP | 扱い |
|---|---|---|
| Landscape320 (320x240) | 320x240 | そのまま。**主にする** |
| Square240 (240x240) | 320x240 の中央 | 左右 40px の額縁 (背景色)。カメラとクリップはホストがオフセット |
| Portrait320 (240x320) | — | 面もスプライトも回転できない。パネルを縦に取り付けてビットマップのみ (座標を入れ替えた BLIT) の限定対応か、このターゲットでは非対応 |

LCD が 800x480 なら、VDP に 400x240 を足して Kessel にも `Wide400` を足す手がある (1 ラインは 1KiB の行に収まる)。

## 7. 細かいこと

- **`cls` を呼ばないゲーム** (`paint`): VDP は `SWAP` で 2 面を使うので、フレームの先頭で前の面を全画面 BLIT で写す (8bpp で 0.6ms)。
  またはエンジンの規則として「キャンバスモード (`screen { persist = true }`) 以外は毎フレーム `cls`」にし、キャンバスモードだけ 1 面で描く
- **`text` / `number`**: 3x5 フォントを 8x8 タイルに 1 文字ずつ入れて VRAM に置き、BLIT4 で描く (1 文字 1 コマンド)
- **`pal` のフェード**: 256 エントリ書き換えで `PAL_WRITE` 256 個 = 2KB/フレーム。問題ない
- **フレームの境界**: `WAIT_VBLANK` → パレット・OAM・面のマップの差分 → `SWAP` → そのフレームの即時描画コマンド、の順 (M9 のデモと同じ)
- **音** (K5a): FPGA の I2S 出力 (MAX98357A、ピン 51/54/55/56) と SDRAM の PCM のリング (BSRAM は使わない)。ホストは 1 フレーム分 (800 標本、3.2KB) を
  `UPLOAD` して `PCM_WR` を進める。Kessel の音は「イベントログ」なので、シンセは RP2350 の 2 つ目のコアで回す
- **帯域の目安** (HSTX 37MB/s = 620KiB/フレーム): スプライト 200 個の BLIT4 = 4KB、`map` を全部 BLIT4 に落としても 1,200 個 = 24KB、ライトマップ 3.6KB、音 1.6KB。SPI 15MHz (31KiB/フレーム) だと `map` の BLIT 落ちだけが苦しい
- **ハーネス v1 で Kessel を回すとき**: 実測の帯域は約 180KB/s (3KB/フレーム)。`LIGHT_WRITE` の全体書き換え (1,202 ワード = 4.7KiB) だけで足りないので、
  変わったセルだけ送る差分にする (1 セル 3 ワード: `LIGHT_WRITE` の先頭 2 ワード + 値。連続するセルはまとめる)

## 8. 検証

- `kessel-vm` のスクリーンを trait にして 2 実装: **ソフトラスタライザ** (今のもの、参照モデル) と **VDP コマンド生成**
- PC では VDP 側の出力を tang-verilog の `gpu_model.py` に通し、同じフレームの画像 (8bpp をパレット展開した RGB565、額縁込み) がソフトラスタライザと一致することをテストにする。
  Kessel の `framebuffer_hash` と VDP の `FRAME_CRC` が同じ画を指すようになる
- 実機では `games/` の各ゲームを数フレーム走らせ、印付きフレームの `FRAME_CRC` を PC と比べる (tang-verilog のシナリオにそのまま入る)
- ライトマップは解像度が変わるので、参照モデル側もセル単位の実装に変えて比べる (ピクセル単位の実装は PC 専用の「高品質」モードとして残してもよい)
- 比べる前に、同じ入力から同じピクセルが出る規則 (10 章) を両側でそろえる。差異はすべてこの規則の問題として 10 章に書き足す
- trait 化のときに、VM 本体を `no_std + alloc` で切れる構造にしておく (RP2350 で `kessel-vm` を動かす E5 で二度手間にならない)

## K1 の結果 (VDP 側)

- `REG_WRITE 22` = `BITMAP_FMT` (0 = RGB565、1 = 8bpp)。描くコマンドにはすぐ効き、表示はラインを始めるときに取り込む (ラインごとに変えられる)
- 8bpp の面: 1 ワードに 4 ピクセル (ピクセル x はバイト x % 4)、1 ラインは 80 ワード。合成器は行を `bm_buf` (BSRAM 1 個) に読み、
  1 クロックに 1 ピクセルずつパレット 0..255 を引いて作業ラインに書く (順位と透過の規則は RGB565 と同じ。透過色は `BITMAP_KEY[7:0]`)。パレットを引くパスが 1 ラインに約 320 クロック増え、読むバーストは 80 ワード短くなる
- 描くコマンド: `CLEAR` / `FILL_RECT` / `POINT` / `DRAW_LINE` は色の `[7:0]`、端はバイトマスク。`BLIT` は 8bpp のソース (透過色 `[7:0]`) と、
  フラグ bit3 で 4bpp のソース (BLIT4、値は `{[11:8], ピクセル}`、透過は値 0)。RGB565 のときの bit3 はエラー
- BLIT のライン バッファはソースの**ワード**を偶数・奇数で分けて置くように変えた。書く 1 ワードのピクセルはソースの隣り合う 2 ワードに収まるので、
  565 / 8bpp / 4bpp のどれでも、描く位置・左右反転によらず 1 クロックに 1 ワード書ける (BSRAM は増えない)
- 検証: シナリオ `k1_8bpp` (8bpp の BLIT・矩形・線・点・クリップ・BLIT4 64 個 / 面 A < ビットマップ (順位 6) < 高優先のスプライト /
  ライン 120 で RGB565 → 8bpp に切り替える印付きフレーム) が モデル = Verilator = 実機。前からのシナリオ 12 個も CRC が変わらず 3 通り一致。
  `tb_gpu` に 8bpp の確認 (ワードの中の 4 つの位置、反転、透過、はみ出し、クリップ、SDRAM の行をまたぐソース)、`tb_line_compositor` に 8bpp のモードを足した
- 実機: selftest 通過、`fps m7_fps` 59.8、`demo` 59.9 fps、`fbtest` 99.7%。1 ラインの合成の最長は 2,057 クロック (e3 の上限 1023 のとき、前と同じ)、k1 は 1,233
- 資源 (E4 → K1): LUT4 6,636 → 7,496、DFF 3,009 → 3,055、BSRAM 40 → 41 / 46。Fmax clk_sys 99MHz、clk_pix 87MHz (目標 63 / 25.2MHz)。
  LUT の増分の多くは BLIT の取り出し (64bit の窓から 4 ピクセル) と矩形のマスクの一般化
- ついでに直したもの: Icarus Verilog が E4 の `line_compositor.sv` (enum の三項演算子) を読めなくなっていたので if に書き換えた

## K2 の結果 (VDP 側)

- **セル順 2 (行優先)**: OAM の word0 `{[10], [30]}` = 2 で、スプライトの中の行 r・列 c のタイルは `先頭 + r x 幅 + c` (3 は予約で、今は 2 と同じ)。
  Kessel の `sprn(id, x, y, w, h, flags)` はそのまま `先頭 = id` の OAM のエントリになる
- **スプライトごとのバンク**: `SPR_BANK` を 4bit にし、`[3]` = 1 のときはパレットの番号が `{0, word1[19:16], ピクセル}` (0..255)。
  8bpp のビットマップ・BLIT4 と同じ番号なので、Kessel の `sprbank` をそのまま書けばよい。モードは全スプライト共通で、ラインごとに切り替えられる
- 検証: シナリオ `k2_sprites` (8bpp + 面 A の上に、行優先・半端な大きさ・反転・スプライトごとのバンク 16 個のスプライト 36 個 /
  同じ OAM を前からのバンクと列優先・表で / ライン 120 でモードを切り替える印付きフレーム) が モデル = Verilator = 実機。前からのシナリオ 13 個も 3 通り一致。
  `tb_sprite_layer` は OAM の乱数にセル順の上位ビットとバンクを入れ、スプライトごとのバンクの掃引を足した (行優先の式やバンクを壊すと落ちることを確かめた)
- 実機: selftest 通過、`fps m7_fps` 59.8、`demo` 59.8 fps。1 ラインの合成の最長は前と同じ 2,057 クロック、k2 は 1,327
- 資源 (K1 → K2): LUT4 7,496 → 7,435、DFF 3,055 → 3,062、BSRAM 41 → 41 / 46。Fmax clk_sys 96MHz、clk_pix 86MHz (目標 63 / 25.2MHz)。
  論理の増分は数十 LUT で、LUT の減りは配置・合成のばらつき

## K3 の結果 (VDP 側)

- `STRETCH_BLIT` (`0x0E`): 引数は `src`、`{dh, dw}`、`{y, x}`、`{sw, stride}`、`sx_step`、`sy_step` (16.16)。最近傍で、描くピクセル (i, j) は
  ソースの `((step >> 1) + i * step) >> 16` を拾う (割り算はホスト)。反転・透過・クリップ・565 / 8bpp / 4bpp のソースは `BLIT` と同じ。描く大きさは 1024 まで
- 作り: 描く 1 行ずつ、(1) ソースの行が変わったときだけ BLIT のライン バッファに読む、(2) 1 クロックに 1 ピクセル拾って描くワードを組み立て、
  行バッファ (BSRAM 1 個、160 ワード x {透過の印 4bit, データ}) に置く、(3) その行をバーストで書く (透過の印とクリップの端はバイトマスク)。
  クリップの外の行は読まない
- `spr_scaled(id, x, y, scale)`: タイル t を `src = base + 8t`、stride 1、sw 8、`dw = dh = 8 x scale`、`step = 8 x 65536 / dw` の 4bpp の `STRETCH_BLIT`
- 速さ (実機、`scenarios/k3_fps.json`): 8bpp の 160x120 → 320x240 が 1 回 1.7ms (200 回で 0.34 秒)
- 検証: シナリオ `k3_stretch` (8bpp: 背景の全画面 2 倍、8x8 のタイルの 1〜5 倍、32x32 の 4bpp の輪の拡大・縮小・非整数倍・反転・透過・クリップ、
  8bpp のソースの縮小 / RGB565: テスト画像の 1/2・拡大・反転、透過色のある玉) が モデル = Verilator = 実機。前からのシナリオ 14 個も 3 通り一致。
  表示の読み出しの待ちは最大 348 クロックのまま。`tb_gpu` に 565 / 8bpp / 4bpp の STRETCH_BLIT (ワードの中の 4 つの位置、行をまたぐソース、上限のエラー) を足した
  (拾う位置の半ピクセルのずらしを外すと落ちることを確かめた)
- 実機: selftest 通過、`fps m7_fps` 60.1、`demo` 59.9 fps
- 資源 (K2 → K3): LUT4 7,435 → 8,434、DFF 3,062 → 3,515、BSRAM 41 → 42 / 46。Fmax clk_sys 92MHz、clk_pix 92MHz (目標 63 / 25.2MHz)。
  見積もり (300〜500 LUT) より多いのは、32bit の累算器 2 組と引数のレジスタ、行バッファへの組み立て (バイトごとの選択) の分
- 合成の回避策: yosys が `STRETCH_BLIT` の累算器のレジスタと名前の付いたワイヤのあいだに `$buf` を残し、nextpnr が置けなかった (E4 の `tpass` と同じ現象)。
  `bufnorm -conn` は SDRAM の IO の名前を変えてしまうので使えず、合成のあとに [`scripts/fix_netlist.py`](../scripts/fix_netlist.py) で
  トップの `$buf` を接続に置き換える (ポートにつながるものはエラーにする)。`make synth` が毎回通す

## K4 の結果 (VDP 側)

- **ライトマップ**: 40 x 30 セル (8 x 8 ピクセル) x {R, G, B} の倍率 6bit (16 = 1 倍)。BSRAM 2 個。`LIGHT_WRITE` (`0x10`) で書き、セル `cy * 40 + cx` から n セル、
  1 ワードに 1 セル (`[5:0]` R、`[13:8]` G、`[21:16]` B)。全体の書き換えは 1,202 ワード (4.7KiB)
- **掛け方**: `LAYER_CTRL` bit5 のラインで、合成の出力 (背景色を含む全部) の各色に `min(最大値, (c * L) >> 4)`。出力のパスで作業ラインと同じクロックにセルを読むので、
  1 ラインの合成の時間は変わらない。ラインごとに切り替えられる (HUD だけ光なし)
- Kessel 側は 5 章のまま: `ambient` / `light` / `shadow_rect` をセルの中心で評価し、倍率を `>> 2` して `LIGHT_WRITE`
- 検証: シナリオ `k4_light` (8bpp の場面 + 面 A + スプライトに ambient・色付きの点光源 3 つ (1 つは上限で切れる)・影の矩形 /
  ライン 224 から光を切る印付きフレーム / RGB565 のテスト画像にセルごとに違う倍率 (1,200 セルの番号の確かめ)) が モデル = Verilator = 実機。
  前からのシナリオ 15 個も 3 通り一致。`tb_line_compositor` に倍率 (0、1 倍、上限で切れる値、背景色) のモード、`tb_gpu` に `LIGHT_WRITE` (2048 で折り返す) を足した
- 実機: selftest 通過、`fps m7_fps` 60.1、`demo` 59.8 fps。1 ラインの合成の最長は 2,057 クロックのまま
- 資源 (K3 → K4): LUT4 8,434 → 8,636 (+202)、DFF 3,515 → 3,522、BSRAM 42 → 44 / 46。乗算 6 個 (1 クロックに 2 ピクセル x 3 色) は LUT で組まれた (DSP は使っていない)。
  Fmax clk_sys 93MHz、clk_pix 115MHz (目標 63 / 25.2MHz)。5 章の見積もり (LUT 500〜800、BSRAM 2) より少ない
- 残りの BSRAM は 2 個。K5 の PCM の FIFO (1 個) で 45 / 46 になる

## K5a の結果 (音)

- **出力**: 基板の MAX98357A に I2S (PA_EN 51、DIN 54、WS 55、BCK 56。Sipeed の `audio` の例と同じ)。54〜56 は SSPI と兼用なので、
  nextpnr に `--vopt sspi_as_gpio`、gowin_pack に `--sspi_as_gpio` を渡す (書き込みは JTAG、起動は MSPI なので SSPI は使っていない)
- **形式と時間**: 48kHz・ステレオ 16bit、BCLK = 32 fs = 1.536MHz。`clk_sys` (63MHz) から累算器 (+128 mod 2625) で作り、映像と同じ PLL なので
  **映像 1 フレームにちょうど 800 標本**。ホストは 1 フレームに 800 標本足せばよく、時計のずれを気にしなくてよい
- **PCM は SDRAM のリング** (pre_K5_review の 1): 既定は SDRAM の最後の 32KiB、2048 標本。アービタに「表示の次」の 1 ワードの読み出しの口を足した。
  BSRAM は増えない (44 / 46 のまま)
- **ホストとの約束**: `UPLOAD` でリングに書き、`REG_WRITE 26 PCM_WR` で書いた数を進める (FIFO の順なのでデータが入ってから進む)。
  `PCM_RD` (0x50) と `UNDERRUN` (0x52) を読める。`AUDIO_CTRL` (23) で開始・停止・空にする。詳しくは SPECIFICATION.md の 12 章
- 検証:
  - `tb_audio_out`: SDRAM の代わり (返すまで 2〜60 クロック) と 16 標本のリングで、標本の順・左右・WS の位置・リングの折り返し・
    使い切ったあとの無音と `UNDERRUN`・BCLK の周期 (41 か 42 クロック)・64 標本がちょうど 84,000 クロック (= 48kHz)・clear を確かめる (左右を入れ替えると落ちる)
  - シナリオ `k5_audio`: 音を出したまま (リングをくり返し読む) k3_stretch と m9_demo の check を流す。CRC はそれぞれと同じ、表示の読み出しの待ちは 348 クロックのまま、
    Verilator で 11,917 標本をアンダーランなしで鳴らした。前からのシナリオ 16 個も 3 通り一致
  - 実機 `harness.py audio --seconds 600 --ring 13 --lead 6000` (750Hz、リングに 1 回書いて `PCM_WR` を進める): **10 分でアンダーラン 0、47,999.9Hz**、
    PCM_RD の読み違い 0。ホストが PCM_RD を読む間隔は最大 45ms
  - 先回り 1,600 標本 (33ms) では 10 分のうちにアンダーランが出た。macOS のホスト (Python + USB) が 45ms 止まることがあるためで、VDP の側ではない
    (同じ時間で再生の速さは 47,997.5Hz、読み違い 0)。RP2350 のホストは止まらないが、先回りは「ホストが止まりうる最長時間 + 1 フレーム」にする
  - **見つけて直した不具合**: `PCM_RD` の 2 バイトがずれることがあった。spi_slave は rdata を取り込んだ次のクロックに re を出すので、
    re のクロックで上位を取っておくと、その 1 クロックで下位から繰り上がったとき 256 ずれる (10 分で数回。ホストの数えが 65,536 狂う)。
    1 クロック前の値を取っておくように直し、`tb_audio_out` に spi_slave と同じ順で読む確かめを足した (前の作りでは落ちる)。
    同じ作りの `FRAME_CRC` (0x05〜0x08) と `CRC_FRAME` も同じように直した (フレームの境目に当たると、下位のバイトだけ前のフレームになりえた)
- **ハーネス v1 で流しきれないもの**: 毎回 `UPLOAD` する流し方 (`--stream`) は 192KB/s 要るが、USB → RP2040 → SPI のブリッジは約 180KB/s で、
  毎秒 3,000 標本ほど足りずに途切れる (再生側は正しい。先回りを置いたループでは 0)。本番の RP2350 は SPI を直接駆動するか HSTX なので足りる
- 資源 (K4 → K5a): LUT4 8,636 → 8,965、DFF 3,522 → 3,746、BSRAM 44 → 44 / 46。Fmax clk_sys 85MHz、clk_pix 249MHz (目標 63 / 25.2MHz)

## 10. 同じ絵を出す規則

Kessel の参照ラスタライザと VDP で、同じ入力から同じピクセルが出るための規則 (K5 の前のレビューで洗い出した)。
方針が「エンジンをハードに寄せる」なので、ずれていれば Kessel 側を直す。決まったものは SPECIFICATION.md の定義が正。

| 項目 | VDP (SPECIFICATION.md) | Kessel | 状態 |
|---|---|---|---|
| `spr_scaled` の拾い方 | `STRETCH_BLIT`: `step = 8 * 65536 / dw` (切り捨て)、列 i は `((step >> 1) + i * step) >> 16` (ピクセルの中心) | 前は `i * 8 / dst` (左端) | ✅ rs-kessel#107 で VDP の式に。反転は描いた結果を鏡にする (ソースの番号を `7 - src` にするのではない。step の切り捨てで `dst = 3` などで違う) |
| 負の座標 | `POINT` `DRAW_LINE` `BLIT` は符号付き。画面の外は描かない | 前は `put_pixel` が x / y を符号なしで読み、負のカメラで負の座標が消えた | ✅ rs-kessel#107 で符号付きに |
| `rect` / `FILL_RECT` の負の座標 | `FILL_RECT` の x, y, w, h は**符号なし** (負の x は大きな正の数になり、何も描かない) | 画面に入る部分を描く | ホストが画面の中に切ってから `FILL_RECT` を出す (VDP は変えない) |
| ライティングの桁 | セル単位 (8 x 8)、**RGB565 の各成分**に `min(最大値, (c * L) >> 4)` (L は 6bit、16 = 1 倍) | ピクセル単位・RGB888 で `c * L / 64` (L は 0..255、64 = 1 倍) | 未決 (Kessel 側の設計が要る)。参照はセル単位・セルの中心で評価・パレットを 565 に落としたあとの成分で同じ式にし、L は `>> 2` で 0..63 に。ピクセル単位は PC 専用の「高品質」モードとして残し、CRC の比較には使わない |
| 線の端点 | `DRAW_LINE` は両端を含む | | 確かめる |
| `rect` の幅・高さ | `FILL_RECT` の w, h はピクセル数 (右下 = x + w - 1) | | 確かめる。`hline` / `vline` の負の長さも |
| `pal()` の RGB888 → 565 | ホストが計算する | | 切り捨てか四捨五入かを 1 つに決める (参照と VDP バックエンドで同じ関数) |
| 透過の規則 | 面のあるフレームだけ `BITMAP_KEY` を有効にし、そのフレームで使われていないインデックスを選ぶ (3 章) | | 参照モデルも同じ手順でインデックスを選ぶ |
| `map()` の割り当て | 面は 2 枚 | | 1 回目・2 回目が面、3 回目以降は BLIT4。フレームの先頭ではなく、呼び出しの順で決まる決定的な規則にする |

`spr_scaled` の違いは縮小で出る (Kessel の前の式は `floor(i * s)`、VDP は `floor((i + 1/2) * s)`、s = 8 / dst)。整数倍の拡大ではどちらも同じ列を拾う。

## 11. その他の申し送り

- `scripts/fix_netlist.py` の `$buf` の回避は、E4 (`tpass`) と K3 (累算器) の 2 回出た。yosys のバージョンを固定して上流に issue を出し、合成のログで残った `$buf` の数を記録する
- E4.5 (スプライトの 1 ラインの個数の上限と x = 0 のマスク、2 セル単位の縦スクロール、H32) はまだ有効。2 セル単位の縦スクロールの値 (VSRAM) は BSRAM を使わず VRAM の中に置く
- BSRAM の見込み: 今 44 / 46。E5 の HSTX 受信の非同期 FIFO で +1 → 45 / 46。その先 (E6 の 2bpp など) は VRAM・SDRAM に置くか、5 章のライトマップの逃げ道を使う
