# G4 着手前のレビュー

G0〜G3 (PR #30〜#33) を読んだ時点でのまとめ。前回は pre_K5_review (採否は [KESSEL_ON_VDP.md](KESSEL_ON_VDP.md) に畳んだ)。計画は [GPU3D_PLAN.md](GPU3D_PLAN.md)。

## 全体への所感

- G1 → G3 で、設計ではなくツールチェーンの問題に 3 種類当たった。どれも「Verilator は通る、nextpnr は OK と言う、実機だけ違う」という、中間のループでしか見つからない種類。
  実機の CRC と複数の配置の種での検証がなければ、G5 のデモで「たまに絵が崩れる」として現れ、原因に辿り着くのに何日もかかった。#33 のコミットを分けた記録は、そのまま教材になる
- 計画からの変更 (ISP / TSP に分けない、キャッシュ 16 行、CLUT 1 組、テクスチャの先頭を大きさの倍数に、3D から BLIT 系を外す) はどれも測定か配置の事実に基づいていて妥当
- 資源 (3D、nextpnr): LUT4 14,334 (69%)、ALU 4,030、**DFF 6,787 (配置の上限 約 7,000 に近い)**、BSRAM 12 / 46、MULT18X18 4。VDP のビットストリームは変わらず (LUT4 10,331、BSRAM 44)

## 1. G3 で分かったツールチェーンの死角 (記録)

| 症状 | 原因 | 回避 |
|---|---|---|
| 配置できない (LUT は足りている) | DFF と制御集合。nextpnr の「LUT4」の数に ALU が入っていない (ALU も LUT の場所を使う) | レコードと頂点の写しをやめて DFF を減らす。資源の記録に DFF と ALU を足す |
| 報告 92MHz で実機のピクセルが化け、化ける場所が種で変わる | nextpnr の Gowin のタイミングモデルに DSP (`MULT18X18`) の経路がない。真のデュアルポート BSRAM (`DPX9B`) の B ポートのアドレスのセットアップが別のセルに登録されている (`gowin_arch_gen.py`)。桁上げの連鎖の見積もりが楽観的 | DSP に 2 クロック、B ポートのアドレスは FF から直接、長い加算は段に分ける。2 つの種で 2 回ずつ通す |
| G1 の三角形が実機だけ落ちる | `RAM16SDP4` (LUT RAM) が実機で値を壊す | `synth_gowin -nolutram` |
| エラーが出ているのにシナリオが合格 | `GPU_STATUS` が読むとエラーを消し、`wait_idle` のポーリングが読み捨てていた | ポーリングで見たビットを OR で残す (#33) |

## 2. 直したことが「2 つの種で通った」という経験則である点

STA が信用できないので、余裕の大きさが分からない。温度・電圧・基板の個体で境界が動く可能性がある (PSDA の取り込み位置と同じ問題)。

- **既知の死角だけを叩く BIST を足す (優先)**: DSP の乗算 (`smul36x18` と同じ使い方) と DP BSRAM の B ポートの読み出し (CLUT やタイルバッファと同じ使い方) を `clk_sys` で回し、
  既知の答えと比べる小さなモジュール。起動時と `selftest` で走らせ、結果 (通った回数、落ちた回数) を `STATUS` 系に出す。
  `memtest` が SDRAM にやっていることを、ロジックの死角に対してやる。基板・温度・種が変わっても「境界に近い」が数秒で分かる
- 温度の掃引: 温めて・冷やして `g3_tex` をループし、BIST の結果と CRC を記録する (PSDA のときと同じ)
- 3D のビットストリームだけ `clk_sys` を 50MHz 程度に落とす選択肢を測っておく (速度の損と引き換えに余裕を買う。数字があれば判断できる)
- エラービットは「読んでも消えない、明示的に消す」に変える。同じ穴が別の経路で開くのを防ぐ

## 3. apicula の不具合は上流に出す

- `DPX9B` の B ポートのセットアップの登録先と、DSP の経路の欠落は、再現する最小の例を添えれば直る種類の問題。直れば「DSP に 2 クロック」「B ポートは FF から直接」の回避策が外せる
- **`MULT18X18` の内蔵レジスタ (入力・出力のパイプライン段) を apicula が使えるかを確かめる**。使えるなら 2 クロックかける必要はなく、
  ビニングのセットアップが 205 → 111 クロック/三角形に戻る。小さい三角形 2,000 個のビニングが 1 フレームの 40% を占めている今、ここが一番大きい速度の損
- `-nolutram` も報告する (実機で壊れる最小の例)

## 4. 制約が変わった: 今は DFF が上限、BSRAM は余っている

BSRAM は 12 / 46。FF に置いている表や写しを BSRAM に寄せる「DFF の減量」を G4 の前に 1 つの PR として。目標は DFF 6,000 以下。

- テクスチャのキャッシュのタグを BSRAM に置き、16 行 → 32〜64 行に。走査の 27% を占めるキャッシュ待ちが減る (16 行 96.3%、32 行 97.5%)
- タイルごとの数、レコードの一時置き、各種カウンタ、`tri_setup` の結果の置き場を BSRAM か 1 本の加算器に
- `TRI` のレコード 32 ワードのうち、タイルのパスで使わないものを書かない (幅を減らす)
- 減量が済んでから G4 (半透明、見込み +600 LUT と相応の DFF)

## 5. 設計の変更の確認

- ISP / TSP に分けない: `g3_tex` でテクセルの取り出しは描いたピクセルの 1.11 倍。重ね描きの多い場面 (G5) で差が開いたら分ける。測定が根拠なので正しい
- テクスチャの先頭を大きさの倍数に (OR でアドレスを作る): ホストの配置の制約が 1 つ増えるだけ。モデルが assert するので事故にならない
- CLUT 1 組、3D から 8bpp・BLIT・BLIT4・STRETCH_BLIT を外す: Kessel は VDP のビットストリームで動くので損はない。3D で画像を描くときはテクスチャの四角形
- `END_SCENE` がタイルのパスの終わりまで待つ (ビニングと描画を重ねない): 2D の記録・再生が要らない。重ねるのは G5 の数字を見てから

## 6. G6 の判断の輪郭 (G5 の数字で確定させる)

| | 見えていること |
|---|---|
| Tang Nano 20K | 3D は動く (LUT 69%、DFF が上限)。VDP との同居は無理 |
| ECP5-25F (iCESugar-Pro) | FF は LUT と同数 (約 24K) で DFF の制約が消える。3D 単体は余裕。VDP (約 10K LUT) との同居は 24K に収まらない見込み |
| ECP5-45F / 85F (Colorlight i9 / ULX3S) | 両方 + CPU コア |

ECP5 では yosys が `MULT18X18D` を推論し、nextpnr-ecp5 のタイミングモデルは DSP と BSRAM を見るので、2 章の死角もかなり減る (ただし新しい基板には新しい死角があるので、BIST は持っていく)。

## 7. 順番

DFF の減量 (キャッシュのタグを BSRAM に) → 死角の BIST + 温度の掃引 → G4 (半透明) → G5 (デモ、即時 vs TBDR の数字) → G6

apicula への報告と `MULT18X18` の内蔵レジスタの確認は並行で。
