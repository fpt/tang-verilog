# エミュレータ向け GPU の方向性 — ラインリスト駆動タイル/スプライトエンジン

[GPU_PLAN.md](GPU_PLAN.md) のコマンド GPU (M5〜M9) を、エミュレータのホストから使えるようにするための検討メモです。
機能・メモリ・スループットの試算を含みます。数値は Tang Nano 20K (GW2AR-18)、`clk_sys` 63MHz、出力 640x480@60Hz を前提にしています。

## 前提と結論

- **ホストが描いたフレームを転送する構成は成り立たない。** 320x240 RGB565 は 150KiB/フレーム = 9.2MB/s。SPI 8MHz (約 1MB/s) では 1 フレームに 150ms かかる。パラレルや HSTX に移っても、ホスト側で 76,800 ピクセル x 60 回を生成する負荷は残る
- **MCU でエミュレータを動かすとき一番重いのはピクセル生成。** CPU・音源はソフトに残し、PPU/VDP (タイル + スプライトの合成) だけを FPGA に出すのが、FPGA のメリットが一番素直に出る形
- **特定機の PPU を複製せず、汎用の「ラインリスト駆動タイル/スプライトエンジン」を作る。** ライン途中のレジスタ変更 (スクロール・パレット・レイヤ有効) をライン番号付きでコマンド列に流す。Amiga の Copper や SNES の HDMA と同じ考え。エミュレータ側は VDP レジスタ書き込みを「ライン番号付きログ」として溜め、VBLANK で VRAM 差分とログをまとめて送る (表示は 1 フレーム遅れる)
- **最初の対象はメガドライブ相当。** 機能が SNES より一回り小さく、ROM が PSRAM に入り、CPU 負荷が現実的。同じエンジンに SMS/GG・PC エンジン・GB/GBC・NES は翻訳層だけで載る。SNES はサブセット (モード 0/1、のちに 7) として後から
- **ホストは固定しない。** トランスポート (SPI / 8080 パラレル / HSTX / FMC) と、コマンドキューの ABI (32bit ワードの列) を分け、どのホストからでも同じ列を投げれば同じ画が出るようにする
- **既存のフレームバッファは「ビットマップレイヤ」として残す。** ホームブリュー向けのコマンド GPU (CLEAR / FILL_RECT / BLIT …) と、タイルエンジンのどちらも同じラインバッファに合成して出す。タイルエンジンに載らない機種はビットマップレイヤへのフレーム転送で動かす (リンクが太ければ)

## 対象機の評価

| 機種 | CPU (ソフト側) | ROM | PPU の特徴 | エンジンへの載せやすさ | 評価 |
|---|---|---|---|---|---|
| NES | 6502 1.8MHz | 〜1MiB (マッパー) | 1 面 + 64 スプライト、2bpp | 容易 | RP2350 単体で 60fps 出るので利点が薄い。翻訳層の練習台には良い |
| GB / GBC | LR35902 4MHz | 〜8MiB | 1 面 + ウィンドウ + 40 スプライト、2bpp | 容易 | 同上 |
| SMS / Game Gear | Z80 3.6MHz | 〜512KiB | 1 面 + 64 スプライト、4bpp、64 色 | 容易 | 軽い。メガドラの前段として自然 |
| PC エンジン | HuC6280 7.2MHz | 〜2.5MiB | 1 面 + 64 スプライト (〜32x64)、4bpp、512 色 | 容易 (大きいスプライト) | CPU が速めだが単純。良い 2 番手 |
| **メガドライブ** | 68000 7.7MHz + Z80 | 0.5〜4MiB | 2 面 + ウィンドウ + 80 スプライト、ライン H スクロール、2 タイル列 V スクロール、優先度、4bpp 64 色、影/ハイライト | **ちょうど良い** | **最初の目標** |
| SNES | 65816 3.6MHz + SPC700 + DSP | 0.5〜6MiB | 4 面、モード 0〜7、128 スプライト、カラー演算、ウィンドウ、HDMA | モード 0/1 は載る。7・演算・ウィンドウは追加実装 | CPU 側も重い。サブセットから |
| NeoGeo / CPS-2 | 68000 12MHz + Z80 | 数十〜数百 MiB | スプライト主体 (NeoGeo は 380 個) | エンジン的には可能 | **ROM が PSRAM に入らない**。対象外 |

評価の 3 条件: (1) PPU を外せば CPU が RP2350 / STM32H7 で足りるか、(2) ROM が PSRAM に入るか、(3) PPU がタイル + スプライトの範囲に収まるか。

## エンジンの機能 (メガドラの上位互換を目標)

| 機能 | 初版 | 備考 |
|---|---|---|
| タイルレイヤ | 2 面 (のちに 4 面) | 8x8 タイル、マップ 32〜128 タイル角、2/4/8bpp、X/Y スクロール、タイル単位の反転・パレット・優先度ビット。SNES モード 0 は 4 面 2bpp、モード 1 は 3 面 |
| ウィンドウ | 1 面を矩形で差し替え | メガドラのウィンドウ、SNES のウィンドウの簡易版 |
| ライン単位のスクロール | レイヤごとに X (と Y) のライン表 | メガドラのラインスクロール、SNES の HDMA の大半はこれ |
| スプライト | 128 個、8〜32px 角 (のちに 64) | 1 ラインあたりの上限は設定可 (メガドラは 20 個 / 320px)。優先度・反転・パレット |
| パレット | 512 x 16bit | メガドラ 64、SNES 256、PC エンジン 512 (BG 256 + スプライト 256) |
| ビットマップレイヤ | 既存の 320x240 RGB565 フレームバッファ | コマンド GPU の描画先。合成の最下層 (または任意の優先度) |
| ライン途中のレジスタ変更 | `WAIT_LINE n` + レジスタ書き込みをコマンド列に混ぜる | パレット差し替え・レイヤ切り替えなどラスタ効果 |
| 横解像度 | 320 と 256 | 256px の機種 (SNES、メガドラ H32、PC エンジン) は 2 倍の 512 を 640 の中央に出す (左右 64px の額縁)。2.5 倍補間は後で |
| その後 | 影/ハイライト、カラー演算 (加算/減算)、アフィン (SNES モード 7)、16x16 タイル | SNES のサブセットを広げるとき |

### コマンドキューの ABI

- 1 コマンド = 32bit ワードの並び (GPU_PLAN.md の `CMD` と同じ)。先頭ワードに opcode と長さ
- 既存: `CLEAR` `FILL_RECT` `DRAW_LINE` `BLIT` `UPLOAD` `SWAP` …
- 追加: `WAIT_LINE n` (ライン n の先頭まで待つ)、`WAIT_VBLANK`、`REG_WRITE addr, value` (エンジンのレジスタ)、`VRAM_WRITE addr, len, data…` (BSRAM の VRAM へ)、`PAL_WRITE`、`OAM_WRITE`
- **トランスポートはバイト列を届けるだけ。** 意味はキューの ABI にだけある。GPU_PLAN.md の「RP2 は描画しない」と同じ原則
- **フロー制御は線で持つ。** `STATUS` の FIFO 残量に加え、`READY` (または `ALMOST_FULL`) の GPIO を 1 本出す。HSTX のような片方向のトランスポートはレジスタを読み返せないため
- 1 フレームぶんのホストの送信順: `WAIT_VBLANK` → VRAM/OAM/パレットの差分 → ライン 0 のレジスタ → `WAIT_LINE k` → レジスタ … → 次の `WAIT_VBLANK`

## メモリ

### VRAM をどこに置くか

タイル描画は 8x8 単位のランダムアクセスで、今の SDRAM 制御 (行アクティブ + 長いバースト) と相性が悪い。

| 置き場所 | 1 タイル行の取得 | 2 面 + スプライトの 1 ライン | 判断 |
|---|---|---|---|
| BSRAM | 1〜2 サイクル | 約 400 サイクル | **既定**。64KiB が入る |
| SDRAM (単発アクセス) | ACT + CL2 + PRE ≈ 8 サイクル | 約 2,000 サイクル (+ 表示読み出し + リフレッシュ) | 2 面なら間に合うが 4 面は苦しい。8bpp の大きいタイルセットや、ホームブリューのアセット用 |

### BSRAM の割り当て (46 ブロック x 16Kbit = 92KiB で見積もり)

| 用途 | 大きさ | ブロック |
|---|---|---|
| VRAM (タイル + マップ) | 64KiB | 32 |
| パレット 512 x 16bit | 1KiB | 1 |
| OAM 128 x 8B | 1KiB | 1 |
| ライン表 240 x 16B (レイヤごとのスクロール等) | 3.75KiB | 2 |
| ラインバッファ 3 本 x 320 x (16bit 色 + 優先度タグ) | 〜2.5KiB | 2 |
| コマンド FIFO | 2KiB | 1 |
| ホスト受信 FIFO | 2KiB | 1 |
| 合計 | | **40 / 46** |

- 余裕が 6 ブロックしかない。既存設計の使用量 (SPI・CRC・フレームバッファ用ラインバッファ) を足して溢れるなら、VRAM を 48KiB から始めるか、マップだけ SDRAM に置く (マップの読み出しはライン内で連続なのでバーストが効く)
- SMS/GG (16KiB)・NES (〜12KiB) は余裕。メガドラ・SNES・PC エンジンは 64KiB が必要
- ロジックは、メガドラ級の VDP を素直に書いて数千 LUT 程度と見込む (20K LUT のうち)。既存の SPI・SDRAM・CRC と合わせても収まる見込みだが、4 面 + カラー演算まで入れたときの実測が必要

### SDRAM (8MiB)

| アドレス | 大きさ | 用途 |
|---|---|---|
| `0x000000` | 512KiB | ビットマップレイヤ (フレームバッファ 2 面)。変更なし |
| `0x080000` | 512KiB | 予備 |
| `0x100000`〜 | 7MiB | ホームブリューのアセット。エミュレータ用途では VRAM の退避や 8bpp タイルセット (任意) |

## スループット

### 1 ラインの描画予算 (FPGA 側)

| 項目 | 値 |
|---|---|
| 走査線 1 本 (800px @ 25.2MHz) | 31.8µs = 63MHz で 2,000 サイクル |
| 論理 1 ライン (縦 2 倍なので走査線 2 本) | 63.6µs = **約 4,000 サイクル** |
| VBLANK (45 本) | 1.43ms = 約 90,000 サイクル |

| 作業 (BSRAM VRAM、ピクセル直列) | サイクル |
|---|---|
| タイルレイヤ 1 面: 41 タイル x (マップ 1 + タイル行 1) + 320px 合成 | 約 400 |
| スプライト: OAM 走査 128 + ライン上限 320px の書き込み | 約 450 |
| ビットマップレイヤ: SDRAM バースト 160 ワード (別ポート、並行) | 約 175 |
| リフレッシュ (7.8µs ごと、論理 1 ラインに約 8 回) | 約 80 (SDRAM 側) |
| **2 面 + スプライト (メガドラ)** | **約 1,300 / 4,000** |
| **4 面 + スプライト (SNES モード 0/1)** | **約 2,100 / 4,000** |

ラインごとの描画は 63MHz のままで収まる。フレームバッファを経由せず、合成したラインをそのまま DVI に出す (ビットマップレイヤだけ SDRAM から読む)。
余裕が足りなくなったら 2px/サイクルの合成か、`clk_sys` を 100MHz 前後に上げる。

### ホストリンク

| トランスポート | 実効 | 1 フレーム (16.7ms) に送れる量 | ホスト |
|---|---|---|---|
| SPI 8MHz | 約 1MB/s | 16KiB | RP2040-Zero (ハーネス) |
| SPI 15MHz (63MHz サンプリングの上限) | 約 1.9MB/s | 31KiB | 同上 |
| 8080 8bit パラレル 25MHz (PIO) | 25MB/s | 410KiB | RP2350 |
| 8080 16bit パラレル 25MHz (PIO) | 50MB/s | 830KiB | RP2350 |
| HSTX 8 レーン DDR | 理論 300MB/s、FPGA 側の受けは 100MB/s 程度まで (要実測) | 1.6MiB 以上 | RP2350 (送信専用、戻りは GPIO) |
| FMC 16bit (メモリマップ、DMA) | 20〜50MB/s 程度 (ウェイト設定次第) | 330〜830KiB | STM32H743 |
| SPI (H7、〜100Mbit) | 約 12MB/s | 200KiB | STM32H743 |

### 1 フレームに必要な量

| モード | 内訳 | 量 / フレーム | 必要帯域 |
|---|---|---|---|
| タイルエンジン、通常 | VRAM 差分 2〜8KiB + OAM 1KiB + レジスタログ 〜0.5KiB | 4〜10KiB | 0.3〜0.6MB/s |
| タイルエンジン、重い (VBLANK 中の大量 DMA、全ラインでラスタ効果) | VRAM 差分 16KiB+ + ログ 240 行 x 8B | 20〜30KiB | 1.2〜1.8MB/s |
| ビットマップ 8bpp (パレット) | 320x240 x 1B | 75KiB | 4.6MB/s |
| ビットマップ RGB565 | 320x240 x 2B | 150KiB | 9.2MB/s |

- **タイルエンジンは SPI 8MHz でも通常は動くが、重いフレームで取りこぼす。** ハーネス (RP2040-Zero) での検証は 15MHz まで上げるか、1 フレームに収まらないシナリオを「遅れてよい」と割り切る
- **ビットマップのフレーム転送は 8bit パラレル 12MHz 以上が必要。** RP2350 の PIO / HSTX、H7 の FMC ならどれも足りる
- ホスト側の負荷: VDP レジスタ書き込みをログに積むのは 1 回数十 ns で、エミュレータの負荷としては無視できる。VRAM 差分はダーティ範囲 (DMA の宛先) を記録して送る

## ホストの抽象化

```
 エミュレータ (68000 / Z80 / 音源 …)      トランスポート              Tang Nano 20K
┌────────────────────────┐   ┌─────────────────────┐   ┌──────────────────────┐
│ VDP 翻訳層             │   │ SPI (RP2040-Zero)   │   │ 受信 FIFO            │
│  reg write → ログ      ├──►│ 8080 / HSTX (RP2350)├──►│  → コマンド FIFO      │
│  DMA → VRAM 差分       │   │ FMC (STM32H743)     │   │  → タイルエンジン      │
│  VBLANK で 1 フレーム送信│   └─────────────────────┘   │     + コマンド GPU     │
└────────────────────────┘        READY (GPIO) ◄────────┤  → ラインバッファ → DVI│
                                                         └──────────────────────┘
```

- 翻訳層は機種ごと (`vdp_md.c`、`vdp_sms.c` …)、トランスポートはボードごと (`link_spi.c`、`link_pio8080.c`、`link_fmc.c`)。間のインターフェースは「32bit ワードを積む / フラッシュする / READY を待つ」だけ
- RP2350: PSRAM に ROM、SRAM に作業領域。PIO で 8080 を出し、空いたコアを音源に
- STM32H743: FMC に GPU をメモリマップし、DMA でキューに流す。外部 SDRAM 付きのボードなら ROM はそこへ
- RP2040-Zero: ハーネス専用のまま。翻訳層のテストは Python の参照モデルと Verilator で行い、実機は SPI の範囲で確認する

## 検証のしかた

GPU_PLAN.md の 3 通り比較をそのまま広げる。

- 参照モデル (`gpu_model.py`) にタイルエンジンの解釈を足す。シナリオはコマンド列なので形式は変わらない
- **実ゲームのフレームをシナリオにする**: PC 上の既存エミュレータに手を入れて、1 フレームぶんの VRAM・OAM・パレットとライン番号付きレジスタログを吐かせ、翻訳層を通してシナリオにする。そのエミュレータの出力画像と `FRAME_CRC` を比べれば、翻訳層とエンジンの両方が実データで検証できる
- ラインごとの予算は Verilator で「各ラインの描画に使ったサイクル数」を数えて、最悪ラインが 4,000 を超えないことをテストにする。実機は `UNDERFLOW_COUNT`

## 段階 (GPU_PLAN.md の M9 のあと、または M7 以降と並行)

| # | 内容 | 完了条件 |
|---|---|---|
| E1 | ライン合成パス: ビットマップレイヤ (既存) をラインバッファに合成する構造に変える。`WAIT_LINE` `WAIT_VBLANK` `READY` 線 | 既存の M4〜M8 のシナリオがそのまま通る。`WAIT_LINE` でラインごとにパレット/色を変えるシナリオが 3 通り一致 |
| E2 | タイルレイヤ 1 面 + パレット + VRAM 書き込み | SMS 相当の画面のシナリオが 3 通り一致。最悪ライン < 4,000 サイクル |
| E3 | スプライト (128 個、ライン上限) | 上限ちょうど・超過・画面端のシナリオが一致 |
| E4 | 2 面目、ウィンドウ、ライン単位スクロール、優先度 | メガドラの実ゲームから取ったフレームが一致 |
| E5 | ホスト翻訳層 (メガドラ) を RP2350 + 8080 で動かす | 実ゲームが 60fps。1 フレームの送信量と READY 待ち時間を記録 |
| E6 | 3〜4 面目、2bpp、256px 横解像度 | SNES モード 0/1 の実ゲームのフレームが一致 |
| E7 | 影/ハイライト、カラー演算、アフィン | 任意 |

E1 が一番大きい構造変更 (フレームバッファ直出しからライン合成へ) なので、M8 の `DRAW_TILEMAP` を作る前に E1 の形にしておくと二度手間にならない。
`DRAW_TILEMAP` は「背景を SDRAM のフレームバッファに描く」コマンドとしてホームブリュー向けに残してもよいし、E2 のタイルレイヤで置き換えてもよい。
