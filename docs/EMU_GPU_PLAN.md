# エミュレータ向け GPU の方向性 — ラインリスト駆動タイル/スプライトエンジン

[GPU_PLAN.md](GPU_PLAN.md) のコマンド GPU (M5〜M9) を、エミュレータのホストから使えるようにするための検討メモです。
機能・メモリ・スループットの試算を含みます。数値は Tang Nano 20K (GW2AR-18)、`clk_sys` 63MHz、出力 640x480@60Hz を前提にしています。

## 前提と結論

- **ホストが描いたフレームを転送する構成は成り立たない。** 320x240 RGB565 は 150KiB/フレーム = 9.2MB/s。SPI 8MHz (約 1MB/s) では 1 フレームに 150ms かかる。パラレルや HSTX に移っても、ホスト側で 76,800 ピクセル x 60 回を生成する負荷は残る
- **MCU でエミュレータを動かすとき一番重いのはピクセル生成。** CPU・音源はソフトに残し、PPU/VDP (タイル + スプライトの合成) だけを FPGA に出すのが、FPGA のメリットが一番素直に出る形
- **特定機の PPU を複製せず、汎用の「ラインリスト駆動タイル/スプライトエンジン」を作る。** ライン途中のレジスタ変更 (スクロール・パレット・レイヤ有効) をライン番号付きでコマンド列に流す。Amiga の Copper や SNES の HDMA と同じ考え。エミュレータ側は VDP レジスタ書き込みを「ライン番号付きログ」として溜め、VBLANK で VRAM 差分とログをまとめて送る (表示は 1 フレーム遅れる)
- **最初の対象はメガドライブ相当。** 機能が SNES より一回り小さく、ROM が PSRAM に入り、CPU 負荷が現実的。同じエンジンに SMS/GG・PC エンジン・GB/GBC・NES は翻訳層だけで載る。SNES はサブセット (モード 0/1、のちに 7) として後から
- **ホストは固定しない。** トランスポート (SPI / 8080 パラレル / HSTX / FMC) と、コマンドキューの ABI (32bit ワードの列) を分け、どのホストからでも同じ列を投げれば同じ画が出るようにする
- **既存のフレームバッファは「ビットマップレイヤ」として残す。** ホームブリュー向けのコマンド GPU (CLEAR / FILL_RECT / BLIT …) と、タイルエンジンのどちらも同じラインバッファに合成して出す。タイルエンジンに載らない機種はビットマップレイヤへのフレーム転送で動かす (リンクが太ければ)

## 対象機の評価

| 機種 | CPU (ソフト側) | ROM | PPU の特徴 | エンジンへの載せやすさ | 評価 |
|---|---|---|---|---|---|
| NES | 6502 1.8MHz | 〜1MiB (マッパー) | 1 面 + 64 スプライト、2bpp | 容易 | RP2350 単体で 60fps 出るので利点が薄い。翻訳層の練習台には良い |
| GB / GBC | LR35902 4MHz | 〜8MiB | 1 面 + ウィンドウ + 40 スプライト、2bpp | 容易 | 同上 |
| SMS / Game Gear | Z80 3.6MHz | 〜512KiB | 1 面 + 64 スプライト、4bpp、64 色 | 容易 | 軽い。メガドラの前段として自然 |
| PC エンジン | HuC6280 7.2MHz | 〜2.5MiB | 1 面 + 64 スプライト (〜32x64)、4bpp、512 色 | 容易 (大きいスプライト) | CPU が速めだが単純。良い 2 番手 |
| **メガドライブ** | 68000 7.7MHz + Z80 | 0.5〜4MiB | 2 面 + ウィンドウ + 80 スプライト、ライン H スクロール、2 タイル列 V スクロール、優先度、4bpp 64 色、影/ハイライト | **ちょうど良い** | **最初の目標** |
| SNES | 65816 3.6MHz + SPC700 + DSP | 0.5〜6MiB | 4 面、モード 0〜7、128 スプライト、カラー演算、ウィンドウ、HDMA | モード 0/1 は載る。7・演算・ウィンドウは追加実装 | CPU 側も重い。サブセットから |
| NeoGeo / CPS-2 | 68000 12MHz + Z80 | 数十〜数百 MiB | スプライト主体 (NeoGeo は 380 個) | エンジン的には可能 | **ROM が PSRAM に入らない**。対象外 |

評価の 3 条件: (1) PPU を外せば CPU が RP2350 / STM32H7 で足りるか、(2) ROM が PSRAM に入るか、(3) PPU がタイル + スプライトの範囲に収まるか。

## エンジンの機能 (メガドラの上位互換を目標)

| 機能 | 初版 | 備考 |
|---|---|---|
| タイルレイヤ | 2 面 (のちに 4 面) | 8x8 タイル、マップ 32〜128 タイル角、2/4/8bpp、X/Y スクロール、タイル単位の反転・パレット・優先度ビット。SNES モード 0 は 4 面 2bpp、モード 1 は 3 面 |
| ウィンドウ | 1 面を矩形で差し替え | メガドラのウィンドウ、SNES のウィンドウの簡易版 |
| ライン単位のスクロール | レイヤごとに X (と Y) のライン表 | メガドラのラインスクロール、SNES の HDMA の大半はこれ |
| スプライト | 128 個、8〜32px 角 (のちに 64) | 1 ラインあたりの上限は設定可 (メガドラは 20 個 / 320px)。優先度・反転・パレット |
| パレット | 512 x 16bit | メガドラ 64、SNES 256、PC エンジン 512 (BG 256 + スプライト 256) |
| ビットマップレイヤ | 既存の 320x240 RGB565 フレームバッファ | コマンド GPU の描画先。合成の最下層 (または任意の優先度) |
| ライン途中のレジスタ変更 | `WAIT_LINE n` + レジスタ書き込みをコマンド列に混ぜる | パレット差し替え・レイヤ切り替えなどラスタ効果 |
| 横解像度 | 320 と 256 | 256px の機種 (SNES、メガドラ H32、PC エンジン) は 2 倍の 512 を 640 の中央に出す (左右 64px の額縁)。2.5 倍補間は後で |
| その後 | アフィン (SNES モード 7、E7)、影/ハイライト、カラー演算 (加算/減算)、16x16 タイル | SNES のサブセットを広げるとき |

### コマンドキューの ABI

- 1 コマンド = 32bit ワードの並び (GPU_PLAN.md の `CMD` と同じ)。先頭ワードに opcode と長さ
- 既存: `CLEAR` `FILL_RECT` `DRAW_LINE` `BLIT` `UPLOAD` `SWAP` …
- 追加: `WAIT_LINE n` (ライン n の先頭まで待つ)、`WAIT_VBLANK`、`REG_WRITE addr, value` (エンジンのレジスタ)、`VRAM_WRITE addr, len, data…` (BSRAM の VRAM へ)、`PAL_WRITE`、`OAM_WRITE`
- **トランスポートはバイト列を届けるだけ。** 意味はキューの ABI にだけある。GPU_PLAN.md の「RP2 は描画しない」と同じ原則
- **フロー制御は線で持つ。** `STATUS` の FIFO 残量に加え、`READY` (または `ALMOST_FULL`) の GPIO を 1 本出す。HSTX のような片方向のトランスポートはレジスタを読み返せないため
- 1 フレームぶんのホストの送信順: `WAIT_VBLANK` → VRAM/OAM/パレットの差分 → ライン 0 のレジスタ → `WAIT_LINE k` → レジスタ … → 次の `WAIT_VBLANK`

## メモリ

### VRAM をどこに置くか

タイル描画は 8x8 単位のランダムアクセスで、今の SDRAM 制御 (行アクティブ + 長いバースト) と相性が悪い。

| 置き場所 | 1 タイル行の取得 | 2 面 + スプライトの 1 ライン | 判断 |
|---|---|---|---|
| BSRAM | 1〜2 サイクル | 約 400 サイクル | **既定**。64KiB が入る |
| SDRAM (単発アクセス) | ACT + CL2 + PRE ≈ 8 サイクル | 約 2,000 サイクル (+ 表示読み出し + リフレッシュ) | 2 面なら間に合うが 4 面は苦しい。8bpp の大きいタイルセットや、ホームブリューのアセット用 |

### BSRAM の割り当て (46 ブロック x 16Kbit = 92KiB で見積もり)

| 用途 | 大きさ | ブロック |
|---|---|---|
| VRAM (タイル + マップ) | 64KiB | 32 |
| パレット 512 x 16bit | 1KiB | 1 |
| OAM 128 x 8B | 1KiB | 1 |
| ライン表 240 x 16B (レイヤごとのスクロール等) | 3.75KiB | 2 |
| ラインバッファ 3 本 x 320 x (16bit 色 + 優先度タグ) | 〜2.5KiB | 2 |
| コマンド FIFO | 2KiB | 1 |
| ホスト受信 FIFO | 2KiB | 1 |
| 合計 | | **40 / 46** |

- 余裕が 6 ブロックしかない。既存設計の使用量 (SPI・CRC・フレームバッファ用ラインバッファ) を足して溢れるなら、VRAM を 48KiB から始めるか、マップだけ SDRAM に置く (マップの読み出しはライン内で連続なのでバーストが効く)
- SMS/GG (16KiB)・NES (〜12KiB) は余裕。メガドラ・SNES・PC エンジンは 64KiB が必要
- ロジックは、メガドラ級の VDP を素直に書いて数千 LUT 程度と見込む (20K LUT のうち)。既存の SPI・SDRAM・CRC と合わせても収まる見込みだが、4 面 + カラー演算まで入れたときの実測が必要

### SDRAM (8MiB)

| アドレス | 大きさ | 用途 |
|---|---|---|
| `0x000000` | 512KiB | ビットマップレイヤ (フレームバッファ 2 面)。変更なし |
| `0x080000` | 512KiB | 予備 |
| `0x100000`〜 | 7MiB | ホームブリューのアセット。エミュレータ用途では VRAM の退避や 8bpp タイルセット (任意) |

## スループット

### 1 ラインの描画予算 (FPGA 側)

| 項目 | 値 |
|---|---|
| 走査線 1 本 (800px @ 25.2MHz) | 31.8µs = 63MHz で 2,000 サイクル |
| 論理 1 ライン (縦 2 倍なので走査線 2 本) | 63.6µs = **約 4,000 サイクル** |
| VBLANK (45 本) | 1.43ms = 約 90,000 サイクル |

| 作業 (BSRAM VRAM、ピクセル直列) | サイクル |
|---|---|
| タイルレイヤ 1 面: 41 タイル x (マップ 1 + タイル行 1) + 320px 合成 | 約 400 |
| スプライト: OAM 走査 128 + ライン上限 320px の書き込み | 約 450 |
| ビットマップレイヤ: SDRAM バースト 160 ワード (別ポート、並行) | 約 175 |
| リフレッシュ (7.8µs ごと、論理 1 ラインに約 8 回) | 約 80 (SDRAM 側) |
| **2 面 + スプライト (メガドラ)** | **約 1,300 / 4,000** |
| **4 面 + スプライト (SNES モード 0/1)** | **約 2,100 / 4,000** |

ラインごとの描画は 63MHz のままで収まる。フレームバッファを経由せず、合成したラインをそのまま DVI に出す (ビットマップレイヤだけ SDRAM から読む)。
余裕が足りなくなったら 2px/サイクルの合成か、`clk_sys` を 100MHz 前後に上げる。

### ホストリンク

| トランスポート | 実効 | 1 フレーム (16.7ms) に送れる量 | ホスト |
|---|---|---|---|
| SPI 8MHz | 約 1MB/s | 16KiB | RP2040-Zero (ハーネス) |
| SPI 15MHz (63MHz サンプリングの上限) | 約 1.9MB/s | 31KiB | 同上 |
| 8080 8bit パラレル 25MHz (PIO) | 25MB/s | 410KiB | RP2350 |
| 8080 16bit パラレル 25MHz (PIO) | 50MB/s | 830KiB | RP2350 |
| HSTX 8 レーン DDR | 理論 300MB/s、FPGA 側の受けは 100MB/s 程度まで (要実測) | 1.6MiB 以上 | RP2350 (送信専用、戻りは GPIO) |
| FMC 16bit (メモリマップ、DMA) | 20〜50MB/s 程度 (ウェイト設定次第) | 330〜830KiB | STM32H743 |
| SPI (H7、〜100Mbit) | 約 12MB/s | 200KiB | STM32H743 |

### 1 フレームに必要な量

| モード | 内訳 | 量 / フレーム | 必要帯域 |
|---|---|---|---|
| タイルエンジン、通常 | VRAM 差分 2〜8KiB + OAM 1KiB + レジスタログ 〜0.5KiB | 4〜10KiB | 0.3〜0.6MB/s |
| タイルエンジン、重い (VBLANK 中の大量 DMA、全ラインでラスタ効果) | VRAM 差分 16KiB+ + ログ 240 行 x 8B | 20〜30KiB | 1.2〜1.8MB/s |
| ビットマップ 8bpp (パレット) | 320x240 x 1B | 75KiB | 4.6MB/s |
| ビットマップ RGB565 | 320x240 x 2B | 150KiB | 9.2MB/s |

- **タイルエンジンは SPI 8MHz でも通常は動くが、重いフレームで取りこぼす。** ハーネス (RP2040-Zero) での検証は 15MHz まで上げるか、1 フレームに収まらないシナリオを「遅れてよい」と割り切る
- **ビットマップのフレーム転送は 8bit パラレル 12MHz 以上が必要。** RP2350 の PIO / HSTX、H7 の FMC ならどれも足りる
- ホスト側の負荷: VDP レジスタ書き込みをログに積むのは 1 回数十 ns で、エミュレータの負荷としては無視できる。VRAM 差分はダーティ範囲 (DMA の宛先) を記録して送る

## ホストの抽象化

```
 エミュレータ (68000 / Z80 / 音源 …)      トランスポート              Tang Nano 20K
┌────────────────────────┐   ┌─────────────────────┐   ┌──────────────────────┐
│ VDP 翻訳層             │   │ SPI (RP2040-Zero)   │   │ 受信 FIFO            │
│  reg write → ログ      ├──►│ HSTX (RP2350)       ├──►│  → コマンド FIFO      │
│  DMA → VRAM 差分       │   │ FMC (STM32H743)     │   │  → タイルエンジン      │
│  VBLANK で 1 フレーム送信│   └─────────────────────┘   │     + コマンド GPU     │
└────────────────────────┘        READY (GPIO) ◄────────┤  → ラインバッファ → DVI│
                                                         └──────────────────────┘
```

- 翻訳層は機種ごと (`vdp_md.c`、`vdp_sms.c` …)、トランスポートはボードごと (`link_spi.c`、`link_hstx.c`、`link_fmc.c`)。間のインターフェースは「32bit ワードを積む / フラッシュする / READY を待つ」だけ
- RP2350: PSRAM に ROM、SRAM に作業領域。HSTX でコマンド列を出し、空いたコアを音源に

### 本番のリンク (RP2350 → Tang Nano 20K、決定)

- **7 本: HSTX のデータ 4 本 + CLK (37.5MHz DDR、約 37MB/s)、READY (GPIO、FPGA → ホスト)、UART TX (FPGA → ホスト、ステータス)**。
  HSTX は送信専用なので、戻りは READY の線と UART だけ
- パケット: マジック (32bit) + 長さ + ペイロード (コマンド FIFO に入れる 32bit ワードの列) + CRC16
  - 受信側はニブル単位でマジックを探して同期する (途中から受けても、ずれても、次のパケットで再同期)
  - CRC が合わないパケットは捨て、エラーのカウンタを上げる (UART のステータスで見える)。再送はしない (次のフレームで上書きされる)
- 8080 パラレルや FMC は候補の比較として上の表に残す
- STM32H743: FMC に GPU をメモリマップし、DMA でキューに流す。外部 SDRAM 付きのボードなら ROM はそこへ
- RP2040-Zero: ハーネス専用のまま。翻訳層のテストは Python の参照モデルと Verilator で行い、実機は SPI の範囲で確認する

## 検証のしかた

GPU_PLAN.md の 3 通り比較をそのまま広げる。

- 参照モデル (`gpu_model.py`) にタイルエンジンの解釈を足す。シナリオはコマンド列なので形式は変わらない
- **実ゲームのフレームをシナリオにする**: PC 上の既存エミュレータに手を入れて、1 フレームぶんの VRAM・OAM・パレットとライン番号付きレジスタログを吐かせ、翻訳層を通してシナリオにする。そのエミュレータの出力画像と `FRAME_CRC` を比べれば、翻訳層とエンジンの両方が実データで検証できる
- ラインごとの予算は Verilator で「各ラインの描画に使ったサイクル数」を数えて、最悪ラインが 4,000 を超えないことをテストにする。実機は `UNDERFLOW_COUNT`

E1 が一番大きい構造変更 (フレームバッファ直出しからライン合成へ) なので、M8 の `DRAW_TILEMAP` を作る前に E1 の形にしておくと二度手間にならない。

### E1 の結果 ✅ (M7 のあと、M8 の前に実施)

- [`line_compositor.sv`](../rtl/vdp/line_compositor.sv) が [`fb_scanout`] を置き換えた。論理ラインごとに、合成を始めるときにレイヤのレジスタを取り込み、
  ビットマップ レイヤ (SDRAM の行をバーストで読み、透過色のピクセルを背景色に置き換える) か背景色で 2 ライン分のライン バッファに書く。
  タイル レイヤとスプライトは、E2・E3 でこの合成にパスを足していく
  - 合成は映像のタイミングが動いていれば常に動く (`CONTROL` bit3 は合成した画面とテストパターンのどちらを出すかだけ)。`WAIT_LINE` が止まらないように
  - 1 ラインの合成は約 340 サイクル (予算 4,000)。ラインの読み出しの待ちの最大は M5〜M7 と同じ 351 サイクル
- レイヤのレジスタ (GPU、`0x48`〜): `BG_COLOR` (背景色)、`LAYER_CTRL` (bit0 ビットマップ有効 = 既定 1、bit1 透過色を有効)、`BITMAP_KEY`。
  既定のままなら出力は今までと同じで、M5〜M7 のシナリオはすべて同じ CRC のまま通った
- GPU のコマンド: `REG_WRITE` (`0x09`、レイヤのレジスタ)、`WAIT_LINE n` (`0x0A`、以降の書き込みがライン n から効くところ = ライン n-1 の合成が
  始まるところまで待つ)、`WAIT_VBLANK` (`0x0B`、= `WAIT_LINE 0`。bit0 で次のフレームに印)
- **印を付けたフレーム**: ラインごとにレジスタを変えるのは、コマンドを流したその 1 フレームだけなので、「GPU が空になって 2 フレーム後」の CRC では比べられない。
  `WAIT_VBLANK` に印を付けると、line_compositor が次のフレームに印を付け、frame_crc がそのフレームの CRC を `MARK_CRC` (`0x0C`) に残して
  `MARK_COUNT` (`0x02`) を増やす。参照モデル・Verilator・実機がちょうどそのフレームを比べる (シナリオの `check_marked`)
- **READY の線**: `CONTROL` bit4 で IRQ ピンを READY (GPU の FIFO が半分以上空いている) にする。`harness.py selftest` が、空なら High、
  `WAIT_LINE` で GPU を止めて 300 ワード積むと Low、空になると High に戻ることを確かめる
- シナリオ `e1_raster`: ラインごとに背景色を変えるラスター バー (透過したビットマップの後ろ) と、帯ごとにレイヤの有効・透過色を変えるフレーム。
  印を付けた 2 フレームと最後の普通の check の 3 つすべてで モデル = Verilator = 実機
- テストベンチ: `tb_line_compositor` (`tb_fb_scanout` を置き換え。ビットマップ・背景色・透過色・ラインごとのレジスタ・line_start の順番・印)、
  `tb_gpu` (`REG_WRITE`、`WAIT_LINE`、`WAIT_VBLANK` の印、READY)、`tb_frame_crc` (印)、`tb_vdp_regs` (`MARK_COUNT` / `MARK_CRC`)
- 途中で見つけた RTL の不具合: frame_crc で、フレームの先頭の判定を画素の積算と同じ if-else の連鎖に入れていたため、VBLANK が終わるクロックに
  画素があると落としていた (実機の映像では最初の画素は 1 クロック後なので表には出ていなかった)。独立した判定に直した

### E2 の結果 ✅

- [`tile_layer.sv`](../rtl/vdp/tile_layer.sv): タイル レイヤ 1 面。VRAM 16K ワード x 32bit (64KiB) とパレット 512 x RGB565 を BSRAM に持ち、
  `line_compositor` がラインの合成を始めるときに動かす。形式:
  - タイルは 8x8・4bpp で、1 行が 1 ワード (左のピクセルが上位の 4bit)。ピクセルの値 0 は透明
  - マップのエントリは 16bit (1 ワードに 2 つ): `[10:0]` タイル番号、`[11]` 左右反転、`[12]` 上下反転、`[14:13]` パレット、`[15]` 優先度 (E2 では使わない)。
    色は パレットの `{バンク (3bit), エントリのパレット (2bit), ピクセルの値 (4bit)}`
  - マップの幅は 32 / 64 / 128 タイル、高さは 32 / 64 / 128 / 28 タイル (28 = SMS の 224 ラインで折り返す)。X / Y スクロールは 10bit
  - 1 タイルごとに マップを読む → タイルの行を読む → 8 ピクセルをパレットを引いて書く。1 ラインは最大 445 クロック
- 合成の順番: タイルのパス (タイル ライン バッファへ) → ビットマップ (または背景色) のパスで、タイルの不透明なピクセルを上に重ねる。
  重なりは下から 背景色 < ビットマップ < タイル。シナリオの最悪ラインは 622 クロック (予算 4,000)
- レジスタ (`REG_WRITE` の番号): `3` TILE_SCROLL_X、`4` TILE_SCROLL_Y、`5` TILE_MAP_BASE、`6` TILE_PAT_BASE (どちらも VRAM のワードアドレス)、
  `7` TILE_CTRL (`[1:0]` 幅、`[3:2]` 高さ、`[6:4]` パレットのバンク)。`LAYER_CTRL` bit2 でタイル レイヤを有効にする。
  どれもラインの合成を始めるときに取り込むので、`WAIT_LINE` + `REG_WRITE` でラインごとのスクロール (ラスター スクロール) ができる
- コマンド: `VRAM_WRITE` (`0x0C`、ワード数 n・VRAM のアドレス・n ワード)、`PAL_WRITE` (`0x0D`、色の数 n・最初の番号・1 ワードに 2 色)。
  どちらも FIFO から 1 ワード読むごとに 1 クロックで書く
- シナリオ `e2_tiles` (モデル = Verilator = 実機、キャプチャも 95% 以上):
  1. SMS 相当の画面: 32x28 のマップ、4bpp のタイル 16 種類 (反転・4 つのパレット)、スクロール (13, 50) で 224 ラインの折り返しが見える
  2. 印を付けたフレーム: 2 ラインごとに横スクロールを変える (波)、ライン 120 でパレットのバンク、ライン 180 で縦スクロールを変える
  3. ビットマップ (テスト画像) の上に、透明のあるタイル (64x32 のマップ、別のバンク、スクロール (300, 5)) を重ねる
- 参照モデル (`gpu_model.py`) に VRAM・パレット・タイル レイヤの合成を足した。シナリオは `tiles` / `tilemap` / `palette` で決まった
  タイル・マップ・色を生成できる。書いていない VRAM やパレットを画面に出すとモデルがエラーにする
- Verilator のシナリオ実行は、1 ラインの合成にかかったクロック数の最大 (`max_line_cycles`) も数え、4,000 未満を合格の条件にした
- 資源 (HDMI、E1 → E2): LUT4 5,455 → 5,955、DFF 2,103 → 2,563、BSRAM 4 → 39 / 46 (VRAM 32、パレット 1、タイル ライン バッファ 2)。
  配置配線のあとの Fmax は `clk_sys` 127MHz (目標 63MHz)、`clk_pix` 93MHz (目標 25.2MHz)。**BSRAM の残りは 7 ブロック**なので、E3 の OAM とスプライトのライン バッファで足りなくなったら
  VRAM を 48KiB にする
- 途中で見つけた RTL の不具合 (M3 からあったもの): `sdram_ctrl` が読み出しの取り込み位置 (`MEM_CFG` の rd_sample) を
  そのまま使っていたので、表示のバースト読み出しの途中で `MEM_CFG` を書くと受け取ったワードの数がずれ、ack が出ずに SDRAM が止まっていた。

### E3 の結果 ✅

- [`sprite_layer.sv`](../rtl/vdp/sprite_layer.sv): スプライト 128 個。OAM は 128 エントリ x 2 ワードの BSRAM 1 個で、GPU の `OAM_WRITE` (`0x0F`) が書く
  - ワード 0: `[9:0]` x (符号付き)、`[25:16]` y (符号付き)、`[27:26]` 幅 - 1、`[29:28]` 高さ - 1 (どちらも 1〜4 タイル)、`[30]` セルの並び順、`[31]` 有効。

  - セルの並び順: 0 = 列優先 (メガドラ、先頭 + 列 x 高さ + 行)、1 = 16 タイル幅の表 (SNES、`{先頭[10:4] + 行, 先頭[3:0] + 列}`)。

  結果は同じで、リスト (64 x 7bit のレジスタ) が要らない。走査 128 + 当たり 1 つに 2 + タイルの列 1 つに 10 クロック
- **ラインの上限はピクセル数** (`SPR_LINE_PX`、8 の倍数に切り捨て = タイルの列の数)。画面の外の列も数え、使い切るとそのスプライトの残りの列と
  後ろのエントリは描かない (メガドラと同じ)。SMS の「1 ライン 8 個」は 64 ピクセルで同じになる
- 合成: **スプライトのパスを最初に**走らせ、作業ラインが空 (順位 0) のところだけ書く。スプライト同士は優先度ビットによらず OAM の前が勝ち、
  その結果の優先度で面と比べる (メガドラ・SNES と同じ。前の低優先スプライトが高優先の面に隠れると、後ろの高優先スプライトも見えない)。

- VRAM とパレットを `tile_layer` から `line_compositor` に移し、読み出しのポートをスプライトとタイルのパスが順番に使う
- 1 ラインの予算をそろえた: ライン 0 の合成を最後から 2 本目のブランキング ラインで始めるようにした (前は最後の 1 本で、ライン 0 だけ予算が半分の
  約 2,000 クロックだった。上限を大きくしたスプライトで足りなくなる)。表示の内容とライン番号の順番は変わらない
- シナリオ `e3_sprites` (モデル = Verilator = 実機):

  2. ラインの上限: 40 列ちょうど (全部出る)、38 列のあとの 4 列幅 (2 列で切れる) とその後ろ (出ない)、画面の外の 30 列が上限を食う、120 列の帯
  3. 印付きフレーム: 帯ごとに上限 64 / 1023 / 0 / 320、パレットのバンクとタイルの場所も変える
  4. 順位 4 のビットマップ (透過色あり) の上下にスプライト
  - 1 と 2 は 1〜2 ピクセルの縞や市松で埋まった画面で、キャプチャは 90〜91% (CRC は完全一致)。シナリオの check に `capture_min` を足して 0.85 にした
- 最悪ラインは 2,055 クロック (上限 1023 = 127 列の帯、予算 4,000)。上限 320 では 1,175。`tb_sprite_layer` の乱数の OAM では上限 320 で最大 473
- M5〜E2.5 のシナリオはすべて同じ CRC のまま (モデル・Verilator・実機)
- 資源 (HDMI、E2.5 → E3): LUT4 6,197 → 6,351、DFF 2,613 → 2,785、BSRAM 39 → 40 (OAM)。配置配線のあとの Fmax は `clk_sys` 119MHz、`clk_pix` 78MHz

## E7 の計画: Mode 7 レイヤと霧

面 A をアフィン変換 (回転・拡大・遠近) で描く「Mode 7 レイヤ」と、遠くを霞ませる「霧」を足す。
SNES の Mode 7 (BG1) をエミュレータから使えること、Kessel から `map` を回転・拡大して描けることの両方を狙う。
前提は E4 まで、[KESSEL_ON_VDP.md](KESSEL_ON_VDP.md) の K5a まで、[SPECIFICATION.md](SPECIFICATION.md)。
(レジスタの名前の `M7_` は SNES の名前。GPU_PLAN.md の段階 M7 とは関係ない)

### 結論

- **今の制約 (BSRAM > リンクの帯域 > ラインの時間 > LUT) のどれにも引っかからない。** VRAM は今の 64KiB に入り (32KiB + 表)、BSRAM は増えず、
  Mode 7 のパスは約 640 クロック (320px) で最悪ラインは約 2,250 (予算 4,000)、LUT は 650〜750 程度
- **行ごとの値は VRAM の表から読む。** 横スクロールの表 (`HSCROLL_BASE`) と同じく、ラインを始めるときに VRAM を数ワード読む。
  SNES の HDMA に近く、フレームの途中にコマンドを流し続けなくてよい。遠近の道路は「行ごとの奥行きの表 + フレームごとの cos / sin」で、
  カメラが回ってもフレームあたりレジスタ数個 (今のハーネス v1 の SPI でも 60fps)。`WAIT_LINE` + `REG_WRITE` も今までどおり使える
- **乗算はラインの先頭で直列に 10 回。** ピクセルごとは加算 (DDA)。シフトと加算の乗算器 1 個 (1 回 16 クロック程度、約 50 LUT) で、
  スプライト・面 B のパスと重ねて動かす
- **霧は K4 のライトマップの出力段を広げる。** セルの倍率に行の倍率を掛け、掛けたあとに行ごとの加算を足す
- **E5 (HSTX) を待たない。** 表を使えば帯域がほとんど要らないので、ハーネス v1 で進められる

### Mode 7: データ

| | 大きさ | VRAM | 備考 |
|---|---|---|---|
| マップ | 128 x 128 セル、1 セル 1 バイト (タイル番号 0..255) | 16KiB、`M7_MAP_BASE` から | 1 ワードに 4 セル (セル n はワード n / 4 のバイト n % 4) |
| タイル | 256 個、8 x 8、8bpp (パレット 0..255、0 は透明) | 16KiB、`M7_PAT_BASE` から | 1 ワードに 4 ピクセル。8bpp のビットマップ・BLIT4 と同じ色の番号 |
| 行列の表 | 1 ライン 2 ワード (直接) か 1 ワード (遠近) | 240〜480 ワード、`M7_TBL_BASE` から | 下の「行ごとの値」 |
| 霧の表 | 1 ライン 1 ワード | 240 ワード、`LINE_FX_BASE` から | 下の「霧」 |

合計で約 34〜35KiB (表を 2 組にしても約 37KiB)。残り (約 27KiB) に面 B のマップ・タイル、スプライトのタイルが入る。

SNES はマップとタイルを VRAM の 1 ワードの下位・上位バイトに交互に置くが、VDP は分けて置く。VDP の VRAM の書き込みは 32bit のワード単位なので、
翻訳層はマップとタイルの写しを持ち、SNES の 1 バイトの書き込みを、そのバイトを含むワードの書き直しにする。

### Mode 7: レジスタ (`REG_WRITE`、値は 16bit)

| 番号 | 名前 | 幅 | 既定 | 意味 |
|---|---|---|---|---|
| 32 | `M7_SEL` | 8 | 0 | **SNES の M7SEL と同じ桁**: bit0 横反転、bit1 縦反転、`[7:6]` マップの外 (0 / 1 折り返す、2 透明、3 タイル 0) |
| 33 | `M7_CTRL` | 4 | 0 | bit0: 面 A を Mode 7 にする、bit1: EXTBG、`[3:2]` 行列の出どころ (0 レジスタ、1 表 (直接)、2 表 (遠近)) |
| 34〜37 | `M7_A` `M7_B` `M7_C` `M7_D` | 16 | 0x0100, 0, 0, 0x0100 | 行列 (符号付き 8.8)。遠近のときは `M7_A` = cos θ、`M7_B` = sin θ (符号付き 8.8 ではなく 1.14) |
| 38 / 39 | `M7_X0` `M7_Y0` | 13 | 0 | 回転の中心 (符号付き、マップのピクセル座標) |
| 40 / 41 | `M7_HOFS` `M7_VOFS` | 13 | 0 | スクロール (符号付き) |
| 42 / 43 | `M7_MAP_BASE` `M7_PAT_BASE` | 14 | 0 | マップ・タイルの VRAM のワードアドレス |
| 44 | `M7_TBL_BASE` | 14 | 0 | 行列の表の VRAM のワードアドレス |
| 45 / 46 | `M7_SX` `M7_SY` | 10 / 9 | 0 | SNES の画面 (0, 0) を置く VDP の画面の位置 (符号付き)。SNES の 256 x 224 を 320 x 240 の (32, 8) に置くなら 32 / 8 |

SNES の `M7SEL` `M7A`〜`M7D` `M7X` `M7Y` `M7HOFS` `M7VOFS` は、2 回書き (下位・上位) を翻訳層で組み立てれば、そのまま写せる。
`M7_SX` / `M7_SY` は 320 x 240 と 256 x 224 の違いを吸収する (スクロールに混ぜると下の clip がずれて、SNES と同じ値にならない)。
E6 の 256px モードが入れば `M7_SX` は 0 のままでよい。

### Mode 7: 計算 (SNES と同じ桁。bsnes の式)

ラインの先頭:

```
  clip(n) = n[13] ? (n | ~1023) : (n & 1023)       14bit の差を 11bit の符号付きにする (SNES の癖)
  h  = clip(HOFS - X0),  v = clip(VOFS - Y0)       (13bit を符号拡張して引く)
  Y  = line - SY                                   縦反転なら 255 - Y
  ox = ((A * h) & ~63) + ((B * v) & ~63) + ((B * Y) & ~63) + (X0 << 8)
  oy = ((C * h) & ~63) + ((D * v) & ~63) + ((D * Y) & ~63) + (Y0 << 8)
  X  = -SX                                         横反転なら 255 + SX、ピクセルごとの増分は -A, -C
  x  = ox + A * X,  y = oy + C * X                 画面の x = 0 の値
```

乗算は 8 回 (遠近なら行列を作る 2 回を足して 10 回)。シフトと加算の乗算器 1 個を直列に使う (1 回 16 クロック、約 160 クロック)。
VRAM の読み出しのポートを使わないので、スプライト・面 B のパスと同時に動かす。最悪ラインでは時間が増えない
(スプライトも面 B もないラインだけ、Mode 7 のパスの前に最大 160 クロック待つ)。x, y は 32bit で持つ (整数部はマップの範囲 1024 より十分大きく、マップの外が折り返して中に見えることはない)。

ピクセルごと (DDA、加算だけ。整数の掛け算をくり返しの足し算にしただけなので SNES と同じ値):

```
  for i in 0..319:
    px = x >> 8, py = y >> 8
    外 = (px | py) & ~1023                         → M7_SEL[7:6] の規則 (2 透明なら書かない、3 ならタイル 0)
    cell = map[(py >> 3 & 127) * 128 + (px >> 3 & 127)]      VRAM 読み 1 回 (バイト選択)
    pix  = pat[cell * 64 + (py & 7) * 8 + (px & 7)]          VRAM 読み 1 回 (バイト選択)
    pix != 0 なら作業ラインに書く
    x += A, y += C                                 (横反転なら -A, -C)
```

- 順位: 面 A と同じ 2 (低)。EXTBG なら `pix[7]` で 2 / 5 を選び、色は `pix[6:0]`
  - SNES の Mode 7 は BG1 の優先度が 1 段で、スプライトの優先度 0 が BG1 の下に来る。VDP ではスプライトは低でも 3 なので、いつも BG1 の上に出る (近似)
  - SNES の EXTBG は BG1 と同時に出せる別の面 (BG2) だが、VDP では面 A 1 つの優先度ビットにする (近似)。ダイレクトカラー (CGWSEL bit0) はやらない
- VRAM の読み出しのポートは 1 つなので、1 ピクセル 2 クロック (マップ、タイルを交互に読むパイプライン)。320px で約 640 クロック。
  マップのデータ → タイルのアドレス → 読み出しが 1 クロックに入らなければ (Fmax が `clk_sys` 63MHz を割りそうなら)、1 ピクセル 3 クロック (約 960) にする
- 面 A のタイルのパス (最大 445) と置き換わるので、最悪ラインは 2,057 → 約 2,250 (スプライトの上限 1023 のとき)
- **ウィンドウ**: ウィンドウは面 A の設定 (タイルの場所・バンク・並び) で描くパスなので、Mode 7 のあいだは描かない (`WIN_H` / `WIN_V` によらずパスを省く)
- `LAYER_CTRL` bit2 (面 A 有効) が 0 なら Mode 7 も描かない

### Mode 7: 行ごとの値 (表)

`M7_CTRL[3:2]` が 0 でなければ、ラインを始めるときに (横スクロールの表と同じく) VRAM から読み、その行だけレジスタの値の代わりに使う。

| `[3:2]` | 表の 1 行 | 行 l のアドレス | 使い方 |
|---|---|---|---|
| 1 直接 | 2 ワード: `{B, A}`、`{D, C}` (下位 16bit が先) | `M7_TBL_BASE + 2 * l` | SNES の HDMA で行列を変えるゲーム。翻訳層は HDMA の表を 1 回の `VRAM_WRITE` にする |
| 2 遠近 | 1 ワード: `[15:0]` 奥行き z (符号なし 8.8) | `M7_TBL_BASE + l` | 道路。A = D = z * cos、B = z * sin、C = -z * sin (cos, sin は `M7_A` / `M7_B`、1.14)。ラインの先頭の乗算 2 回 |

- 遠近の z の表は、地平線 h、カメラの高さ H、拡大 k に対して行 l (> h) で z = k * H / (l - h)。カメラの高さと地平線が変わらなければ表は書き換えない。
  向きを変えるのは `M7_A` / `M7_B` の 2 つ、位置は `M7_X0` `M7_Y0` `M7_HOFS` `M7_VOFS` (フレームに 1 回、`WAIT_VBLANK` のあと)
- 地平線より上は、表の行の z を 0 にする (行列が 0 になり、全部マップの (X0, Y0) の 1 点になる) のではなく、`WAIT_LINE` で `M7_CTRL` bit0 を切り替えて
  面 A (通常のタイル) か背景色にする
- 表の書き換えはすぐ効く (VRAM と同じ)。表示中に書き換えると途中の行から変わるので、2 組の表を置き、書き終えたほうに `M7_TBL_BASE` を
  `WAIT_VBLANK` のあとの `REG_WRITE` で切り替える
- `WAIT_LINE n` + `REG_WRITE` も今までどおりライン n から効く (表を使わないとき)。こちらは 1 行 5 ワード、240 行で約 1,200 ワード (4.8KB) になり、
  コマンド FIFO (512 ワード) より多いのでフレームの先頭から順に流し続ける必要がある。ハーネス v1 (実測約 180KB/s = 3KB/フレーム) では 60fps に足りない

### 霧 (遠くを霞ませる)

霧は「ピクセルの色を、行ごとに決まる割合 f で霧の色に寄せる」: `out = c * (1 - f) + fog * f`。
第 1 項は K4 のライトマップと同じ形 (倍率が 1 - f) で、第 2 項 `fog * f` は**行の中で定数**。出力段を次のように広げる:

```
  out   = min(最大値, ((c * L_eff) >> 4) + ADD)      成分ごと (R, B は 5bit、G は 6bit)
  L_eff = min(63, (L_cell * L_line) >> 4)          成分ごと。ライトマップが無効 (LAYER_CTRL bit5 = 0) なら L_cell = 16
```

| 番号 | 名前 | 幅 | 既定 | 意味 |
|---|---|---|---|---|
| 47 | `LINE_MUL` | 15 | 0x4210 | 行の倍率: `[4:0]` R、`[9:5]` G、`[14:10]` B (16 = 1 倍、31 = 1.94 倍) |
| 48 | `LINE_ADD` | 16 | 0 | 行の加算 (RGB565、成分ごとに足して飽和) |
| 49 | `LINE_FX_CTRL` | 1 | 0 | bit0: `LINE_MUL` / `LINE_ADD` を表から読む |
| 50 | `LINE_FX_BASE` | 14 | 0 | 霧の表の VRAM のワードアドレス。行 l は `LINE_FX_BASE + l` の 1 ワード `{LINE_ADD [31:16], LINE_MUL [14:0]}` |

- 回路: 出力のパスは 1 ワード (2 ピクセル、同じセル) ごとにライトマップのセル (`lm_q`) を読んでいる。ここに 1 段足して `L_eff` (5bit x 6bit の乗算 3 個、
  2 ピクセルで共有) を出し、次の段で今の `lit()` のあとに加算と飽和を入れる。表 (40 セル分の `L_eff`) は作らない。合成の時間は 1〜2 クロックしか増えない
- `L_eff` は 63 で飽和する (`L_cell` 63 と `L_line` 31 で 122 になるのを切る)。`L_line` が 5bit なので、霧の段階は 1/16 刻み (RGB565 の色の段階と同じ程度)
- 既定 (`LINE_MUL` = 16 x 3、`LINE_ADD` = 0) なら出力は今と同じで、前からのシナリオの CRC は変わらない
- 使い方:
  - 霧: 行 l の割合 f (0..1、遠いほど大きい) に対して `LINE_MUL = 16 * (1 - f)`、`LINE_ADD = fog * f`。道路なら z の表と一緒に霧の表を 1 回書く
  - 暗転・フェード: 全行同じ `LINE_MUL` を 1 回書くだけ (ライトマップを書き換えなくてよい)。色付きのフラッシュは R/G/B 別の倍率か `LINE_ADD`
  - 夜の霧: ライトマップ (ランプ) と霧 (行) が同時に効く
  - SNES の `COLDATA` の固定色の加算 (半透明なし) は `LINE_ADD` で近似できる。減算・半透明は E8

### Kessel から

| Kessel の API (案) | VDP |
|---|---|
| `map7(a, b, c, d, x0, y0, hofs, vofs)` | 面 A を Mode 7 にして行列を書く。引数は 8.8 固定小数点 (Kessel の `scale` と同じ桁) |
| `map7_lines(table)` | 行ごとの行列。直接の表を VRAM に書いて `M7_CTRL[3:2]` = 1 |
| `road(horizon, height, yaw, zoom)` | 遠近の表。z の表は horizon / height / zoom が変わったときだけ書き、yaw は `M7_A` / `M7_B` |
| `fog(colour, near, far)` | 行ごとの f を奥行きから計算し、霧の表を書く。`colour` はパレットの番号 (565 に展開して `LINE_ADD` に) |
| `fade(f)` | 全行の `LINE_MUL` |

- Mode 7 のタイルは 8bpp。Kessel のシートは 4bpp なので、`map7` 用のタイルは BLIT4 と同じ `bank * 16 + nibble` でホストが 8bpp に展開して VRAM に置く (ROM のロード時に 1 回)
- `map7` は面 A を使うので、そのフレームの `map()` は 1 回まで (面 B)。ウィンドウ (面 A の設定で描く) も使えない
- `outrun` は道路を `hline` で描いているが、`road` + `fog` に置き換えると帯域も見た目も良くなる。`spr_scaled` の車はそのまま
- 参照モデル (Kessel 側の Mode 7) は上の固定小数点の式 (clip と `& ~63` を含む) をそのまま使う (`spr_scaled` のときと同じ教訓)

### 検証

- `gpu_model.py` に上の式 (clip、`& ~63`、遠近の行列、`L_eff` の飽和、加算の飽和) を同じ桁で入れる
- シナリオ `e7_mode7`:
  - 単位行列・スクロールだけ (同じ絵を 8bpp のビットマップで描いた CRC と一致することを確かめる)
  - 90 度回転・2 倍・1/2 (境界のピクセルの拾い方)、clip が効く大きなスクロール
  - マップの外の 3 モード、横反転・縦反転、`M7_SX` / `M7_SY`、EXTBG の優先度でスプライトとの重なり
  - 直接の表 (行ごとの行列)、遠近の表 + 霧の表の印付きフレーム、表を 2 組で切り替え
  - ライトマップ + 霧の同時 (夜の道路)、`LINE_MUL` / `LINE_ADD` の飽和
- `tb_line_compositor`: 行列の掃引 (ランダムな A〜D、X0 / Y0、HOFS / VOFS、SX / SY、反転) で参照の式と一致
- 実機: selftest、`fps` 60、遠近の道路を回しながら 60fps (ハーネス v1)、Mode 7 が足す合成の時間が約 200 以下、前からのシナリオ (K5a までの 17 個) の CRC が変わらない

### 順番

表を使うので、E7 は E5 (HSTX) を待たずにハーネス v1 で進められる。Mode 7 のパス → 表 → 霧の順に作り、それぞれでシナリオを足す。
Kessel 側の `map7` / `road` / `fog` は、Kessel 側の K1〜K4 (trait 化と VDP バックエンド) が通ったあと。
