# 開発計画 — SDRAM フレームバッファの tiny-GPU

Tang Nano 20K のパッケージ内 SDRAM にフレームバッファを置き、図形 (矩形・線)・スプライト・背景をコマンドで描く小さな GPU を作る計画です。
開発は [HARNESS.md](HARNESS.md) のハーネス (RP2 + HDMI キャプチャ) で検証しながら進めます。

[ARCHITECTURE.md](ARCHITECTURE.md) の「フレームバッファを持たず、走査しながら生成する」方針からの転換です。
「レジスタバスの先に VDP がある」「SPI はレジスタバスへの変換器」「RP2 は描画しない」はそのまま引き継ぎます。
ARCHITECTURE.md は M3 (SDRAM) が通ったので書き直しました。

## 方針

1. **RP2 のファームウェアは早い段階で固定する。** UF2 の書き込みが面倒なので、RP2 は「状態を見る + SPI を素通しする」だけのブリッジにして、
   GPU のレジスタやコマンドの意味はすべてホスト側 (Python) に置く。GPU を作り変えても RP2 を書き直さずに済む
2. **画は 3 通りで突き合わせる。** 同じシナリオ (コマンド列) から
   (a) Python の参照モデル、(b) Verilator の RTL シミュレーション、(c) 実機を動かし、
   (a)=(b) はピクセル完全一致、(a)=(c) は `FRAME_CRC` で完全一致、HDMI キャプチャは許容誤差付きで比べる
3. **リスクの大きい SDRAM を先に確かめる。** → M3 で確認済み。オープンソースのツールチェーンでパッケージ内 SDRAM が動いた (後述)
4. **ハーネスの線は「Low = 何もしていない」にそろえる。** RP2 は毎回ピンを入力 + プルダウンに戻すので、
   プルダウンされた状態が「リセット中」や「選択中」にならないようにする (M0 で CS_N / RESET_N の極性を変える)

## 決めること (初期値)

| 項目 | 初期値 | 理由 |
| --- | --- | --- |
| 論理解像度 | 320x240、縦横 2 倍で 640x480 に出す | 帯域とメモリが 1/4 で済み、レトロ機らしい。後で 640x480 にも上げられる |
| ピクセル形式 | RGB565 (2 ピクセル / 32bit ワード) | SDRAM が 32bit 幅。パレットは後で |
| フレームバッファ | 2 枚 (表示用と描画用)、VBLANK で切り替え | ちらつき防止 |
| メモリ配置 | 1 ライン = 1KiB (320 ピクセル + 余り) = SDRAM の 1 行 | 1 ラインを 1 回の行アクティブ + バーストで読める |
| GPU / SDRAM クロック | 63MHz (既存の 126MHz を CLKDIV /2) | まずは余裕のある速さで。足りなければ別の rPLL で上げる |
| SPI | 最初 1MHz、M1 で 4〜8MHz まで確認 | FPGA 側は 63MHz で SCK をサンプリングするので上限は 15MHz 程度 |

### メモリ配置

パッケージ内 SDRAM は 64Mbit (2M ワード x 32bit、4 バンク x 2048 行 x 256 列)。

| アドレス (バイト) | 大きさ | 用途 |
| --- | --- | --- |
| `0x000000` | 256KiB | フレームバッファ 0 (240 ライン x 1KiB) |
| `0x040000` | 256KiB | フレームバッファ 1 |
| `0x080000` | 512KiB | 予備 (640x480 にするとき用) |
| `0x100000`〜 | 7MiB | アセット (スプライト・タイル・背景画像)。ホストが `UPLOAD` で書き込む |

### 帯域の見積もり

| 用途 | 帯域 |
| --- | --- |
| SDRAM のピーク (63MHz x 4B) | 252MB/s (実効はその半分程度と見る) |
| 表示の読み出し (320x240 x 2B x 60Hz、1 ラインを 2 回表示) | 9.2MB/s |
| 全画面クリア 1 回 | 150KiB / フレーム |
| 16x16 スプライト 64 枚 (読み + 書き) | 64KiB / フレーム |

1 フレームあたり全画面の塗りつぶし 10 回分以上の余裕があります。表示の読み出しを最優先にし、
間に合わなかったら `UNDERFLOW_COUNT` を数えて見えるようにします (調査が楽になる)。

## RP2 ブリッジファームウェア

`harness/firmware/` の配線テストを発展させ、次のコマンドだけを持つブリッジにします。1 行 1 コマンドのテキスト、応答は 1 行 JSON。

| コマンド | 内容 |
| --- | --- |
| `ping` | ファームウェア名・版・ボード |
| `status` | 全ハーネスピンの値、HEARTBEAT / VSYNC の実測周波数、IRQ・ERROR、ready 判定、SPI 周波数、各種カウンタ |
| `spi <hex>` | CS を立てて送受信し、受信を hex で返す (1 行 4KiB まで)。ready でなければ何も駆動せずエラー |
| `freq <hz>` | SPI の周波数 |
| `reset <ms>` | RESET を指定時間 High にする |
| `irqwait <ms>` | IRQ (VBLANK) の立ち上がりを待つ。フレームに同期した操作用 |
| `wiretest` | 今の配線テスト (FPGA に `harness_probe` を入れたとき) |

- レジスタの番地もコマンドの形式も知らない。ホストが組み立てた SPI のバイト列を流すだけ
- **ready**: HEARTBEAT が直近 100ms 以内にトグルしているときだけ SPI 線を駆動する。FPGA の書き込み中や、別の設計が入っているときは駆動しない
- **ピンの扱い**: トランザクションの間だけ SPI 機能にし、終わったら入力 + プルダウンに戻す (配線テストと同じ約束)
- 一度書き込んだら、原則として書き換えない。書き換えるのはブリッジ自体のバグや、新しい観測機能が必要になったときだけ

### ハーネスの線の極性を変える (M0)

RP2 がピンを手放すとプルダウンで Low になるので、Low が「何もしていない」になるようにします。

| 今 | 変更後 | 理由 |
| --- | --- | --- |
| `CS_N` (負論理) | `CS` (正論理) | プルダウン中に FPGA が「選択された」と思わないように |
| `RESET_N` (負論理) | `RESET` (正論理) | プルダウン中に FPGA がリセットされ続けないように |
| `IRQ_N` (負論理) | `IRQ` (正論理) | 合わせておく |

CS はもともと GPIO で動かしているので、RP2 のハードウェア SPI の都合はありません。`harness/pins.json`・HARNESS.md・WIRING.md を合わせて直します。

## ホスト側

`tools/harness/` に Python (標準ライブラリだけ) で作ります。USB を使うので macOS のホストで直接動かします
(Docker Desktop から USB が見えないため。`openFPGALoader` と同じ扱いの例外として CLAUDE.md に書き足す)。

| サブコマンド | 内容 |
| --- | --- |
| `harness status` | ブリッジの `status` |
| `harness reg read/write` | レジスタの読み書き (レジスタマップはここで持つ) |
| `harness prog <fs>` | `make pincheck` を通してから `openFPGALoader` で SRAM に書き込む |
| `harness selftest` | HARNESS.md の selftest (ID・SCRATCH 往復・HEARTBEAT・VSYNC・RESET) |
| `harness run <scenario.json>` | シナリオを SPI 列にして実行し、`FRAME_CRC` を読み、キャプチャし、参照と比べる |
| `harness capture` | `ffmpeg -f avfoundation` で 1 フレームを rgb24 の生データで取り込む |

- **シナリオ** (`scenarios/*.json`): GPU コマンドの列。同じファイルを参照モデル・Verilator テストベンチ・実機が読む
- **参照モデル** (`tools/harness/gpu_model.py`): コマンドを解釈して 320x240 の画像と、出力 640x480 の CRC32 を作る
- 出力は 1 つの JSON (各段階の pass/fail・CRC・差分の割合) と差分 PNG。エージェントはこれだけ読めばよい
- `make hw-test SCENARIO=...` で、ビットストリーム・render (Docker) → `harness run` (ホスト) を 1 回で回す

### キャプチャとの比較

MS2109 は YUV (4:2:2、リミテッドレンジ) を通るので、色が少しずれ、横方向に色がにじみます
(HDMI のテストパターンを取り込んだとき、`#303040` が暗く写っていた)。そこで:

- 正しさの判定は `FRAME_CRC` (完全一致) で行い、キャプチャは「実際に画面に出ているか」の確認に使う
- **実装 (M2)**: [`tools/harness/imgcmp.py`](../tools/harness/imgcmp.py)。`harness.py frametest` から使う
  - 640x480 のまま取り込める (MS2109 が 640x480 を出せる)。最初の 5 フレームは捨てる
  - 比べるたびに、チャンネルごとの「キャプチャ ≒ 倍率 x 参照 + オフセット」を最小二乗で求めて補正する (実測は倍率 0.97〜1.01、オフセット -6〜+1)
  - 色の境目から横 2 ピクセル・縦 1 ライン以内は必ずにじむので割合から外し、別に数える。それ以外で「補正後の差が 40 以内のピクセルが 99% 以上」を合格にする
  - 差分 PNG: 合っているところは暗い灰色、境目のにじみは黄色、それ以外の不一致は赤
  - 結果 (テストパターン): 境目以外は 100% 一致、境目 (画面の 19%) は 92.5% 一致
- キャプチャデバイスは番号ではなく名前 (`-i "USB3. 0 capture:none"`、環境変数 `HARNESS_CAPTURE` で変更) で選ぶ。
  番号は一覧と実際に開くときで変わることがあり、別のカメラを開いてしまった

### M5 の範囲 ([pre_M5_review.md](pre_M5_review.md) を受けて)

1. ✅ **SDRAM クロックの位相調整** (下の「M5 の前に: SDRAM クロックの位相」)
2. ✅ **書き込みのバーストとバイトマスク**: `sdram_ctrl` に同じ行の中の書き込みバースト (最大 64 ワード) と、ワードごとの `wmask[3:0]` (DQM) を足す。
   SDR SDRAM の書き込みの DQM は同じクロックのデータに効くので、奇数の x で始まる / 終わる `FILL_RECT` の端や、M7 の `BLIT` の透過色を
   読み‐修正‐書きなしで書き飛ばせる。描画側のバーストを 64 ワードで切ると、表示の読み出しを待たせるのは最大 1µs 程度
3. ✅ **`FB_BASE` はフレームに 1 回だけ取り込む**: 今の `fb_scanout` はラインを読むたびに `FB_BASE` を見ているので、フレームの途中で変えると
   上下で別の面が混ざる。ライン 0 を先読みするとき (最後のブランキング ライン) に取り込み、`SWAP` はそこで完了する。
   `FRAME_CRC` のスナップショットには、どのフレームの CRC かがわかるようにフレーム番号も入れ、参照モデルもフレーム番号付きで比べる
4. ✅ **コマンド FIFO** (BSRAM): `CLEAR` `FILL_RECT` `SWAP` `UPLOAD`。`STATUS` に FIFO の空き容量を出し、ホストはその分だけ送る
   (ブリッジの `spi` 1 回 = 最大 4KiB)。`UPLOAD` もコマンドの 1 つなので、M4 のアップロード用ポート (`0x30`) は置き換える
5. ✅ **参照モデルと最悪ケースのテスト**: Python の参照モデル (`gpu_model.py`) がシナリオから画像とフレーム番号付きの CRC を作る。
   Verilator で、描画バーストが最長のときの表示の読み出しの待ち時間を数え、`UNDERFLOW` が出ないことをテストにする

表示のライン読み出しの締め切りは、ソースの 1 ラインを出力で 2 ライン表示するので 2 ライン分 (63.5µs)。読み出し自体は約 2.7µs なので、
描画のバーストで待たされても余裕は大きい (表示の要求で描画バーストを中断する仕組みは作らない)。

### M7 のあと: E1 (ラインごとの合成) ✅

M8 の前に、[EMU_GPU_PLAN.md](EMU_GPU_PLAN.md) の E1 を先に行った。表示は `fb_scanout` (フレームバッファを直接出す) から
`line_compositor` (ラインごとにレイヤを合成する) に変わり、`REG_WRITE` / `WAIT_LINE` / `WAIT_VBLANK` と READY の線が増えた。結果は EMU_GPU_PLAN.md の「E1 の結果」。
続けて E2 (タイル レイヤ 1 面、`VRAM_WRITE` / `PAL_WRITE`) も行った (「E2 の結果」)。M8 の `DRAW_TILEMAP` は、タイル レイヤがあるので
「タイルをフレームバッファに描く」ホームブリュー向けのコマンドとして残すか、やめるかを M8 の前に決める

### M7 の結果 ✅

- [`gpu.sv`](../rtl/vdp/gpu.sv) に `BLIT` (`0x08`) を足した。引数は ソースのワードアドレス、`{h, w}`、描く位置 `{y, x}` (符号付き)、ソースの行のワード数 (stride)。
  先頭ワードにフラグ (透過・左右反転・上下反転) と透過色
  - 1 行ずつ: ソースの行をバーストで読んでライン バッファに置き、描く行を 64 ワードずつのバーストで書く。ソースの行が SDRAM の行をまたぐときは読み出しを分ける
  - ライン バッファは偶数番目と奇数番目のピクセルを別の BSRAM に置く。書くワードの 2 ピクセルを 1 クロックで読めるので、描く位置が奇数でも、
    左右反転でも、1 クロック 1 ワードで書ける。透過色・クリップ・矩形の端はバイトマスク (DQM) で書き飛ばす (読み‐修正‐書きはしない)
  - 上下反転は、ソースの行を下から読む。最初の行のアドレスは掛け算を使わず stride を足して求める
  - コマンドの引数は 4 ワードまで読めるようにした。GPU は SDRAM の読み出し (`rvalid` / `rdata`) も使うようになった
- 参照モデル: `BLIT` と、シナリオ用の決まったスプライト (`upload_sprite`: 矢印・円・縞) を足した
- テストベンチ (`tb_gpu`): 偶数 / 奇数の位置、左右・上下反転、透過、画面の外 (左上・右下)、SDRAM の行をまたぐソース、クリップを全ピクセル比べる。
  `+trace` で GPU の状態とメモリの要求を表示できる。最初の失敗は、ソースを描く面 (ワードアドレス 0x10000〜) に置いていて CLEAR で消えていた
  テストベンチの間違いだった
- シナリオ (モデル = Verilator = 実機):
  - `m7_blit`: 全画面 (320x240) の背景 `BLIT`、偶数 / 奇数の位置 x 反転 4 通り x 透過あり / なし、画面の外 (部分 / 全部)、行をまたぐソース、クリップ。
    2 つ目の check は背景 + 64 スプライト
  - `m7_frames`: 背景 + 64 スプライトを 8 フレーム続け、4 フレーム目と 8 フレーム目を比べる
- **性能** (`harness.py fps scenarios/m7_fps.json`): 毎フレーム 全画面の背景 `BLIT` + 16x16 を 64 枚 + `SWAP` を 120 フレーム続けて、
  **60.2fps、表示 1 フレームに描画 1 フレーム、`UNDERFLOW` 0** (1 フレーム 326 ワード)
- キャプチャの合格線: シナリオでは 95% にした。正しさは `FRAME_CRC` で決め (完全一致)、キャプチャは「画面に出ているか」を見るためのもの。
  64 スプライトの画面は、グラデーションの色変換の非線形と、スプライトの縁の 4:2:2 のにじみで 98.98% だった (CRC は完全一致)
- 資源: LUT 24%、BSRAM 4 個、`clk_sys` の最大 128MHz (必要 63MHz)。SDRAM の位相の余裕は前 4 段・後ろ 3 段

### M6 の結果 ✅

- [`gpu.sv`](../rtl/vdp/gpu.sv) に `POINT` (`0x05`)、`DRAW_LINE` (`0x06`)、`CLIP` (`0x07`) を足した
  - `DRAW_LINE`: 整数のブレゼンハム (err = dx + dy、e2 = 2 err)。両端を含む。座標は符号付き 16bit で、画面の外から始まる線もよい。
    クリップ矩形の中のピクセルだけをバイトマスク付きの 1 ワード書き込みで書き、外のピクセルは書かずに進む (±30000 の線でも 1ms 程度)
  - `POINT`: 同じ点から同じ点への線
  - `CLIP`: 両端を含む矩形。`FILL_RECT` / `POINT` / `DRAW_LINE` に効き、`CLEAR` には効かない。画面の外は端に丸め、
    x0 / y0 が画面の外なら空 (何も描かない)。既定は画面全体
  - コマンドの引数の読み方を 1 つの仕組み (先頭ワード + 0〜2 ワード) にまとめた
- 参照モデル ([`gpu_model.py`](../tools/harness/gpu_model.py)) に同じ規則のブレゼンハムとクリップを足した。シナリオの `point` / `line` / `clip`
- テストベンチ (`tb_gpu`): 320x16 の画面で、8 方向・水平・垂直・1 点・画面の外からの線、点、クリップ、空のクリップ、`CLEAR` が
  クリップに関係ないことを、テストベンチ側のブレゼンハムで作った期待値と全ピクセル比べる。
  テストベンチの `cmd` もホストと同じく `GPU_FREE` を見てから送るようにした (16 ワードの FIFO があふれてコマンドがずれ、止まっていた)
- シナリオ `m6_lines` (32 方向の星形、ちょうど 45 度、画面の 4 辺、画面の外から外、全部画面の外、±30000 の長い線、1 点、角の点と外の点、
  クリップ矩形と矩形・線・点、空のクリップ、元に戻す): 3 つの check すべてで モデル = Verilator = 実機。キャプチャ 99.5〜100%、`UNDERFLOW` 0
- 資源: LUT 19%、`clk_sys` の最大 121MHz (必要 63MHz)。SDRAM の位相の余裕は前後 3 段ずつ (M5 は 4 / 3。配置が変わったため。2 段以上なので合格)

### M5 の結果 ✅

- [`gpu.sv`](../rtl/vdp/gpu.sv): コマンド FIFO (512 ワード、BSRAM) と `CLEAR` `FILL_RECT` `SWAP` `UPLOAD`。レジスタは `0x30` (コマンドのポート)、
  `0x40` `GPU_STATUS`、`0x41` `GPU_FREE`、`0x44` `FB_BASE`、`0x46` `DRAW_BASE` (`FB_BASE` は `vdp_regs` から移した)。
  M4 のアップロード用ポートは `UPLOAD` コマンドに置き換えた
- `sdram_ctrl` に書き込みのバースト (同じ行、最大 64 ワード) とワードごとのバイトマスク (DQM)。`sdram_arb` は 3 者 (表示 > GPU > メモリテスト)
- `fb_scanout` は `FB_BASE` をライン 0 を読み始めるときにだけ取り込み、そのことを `base_latched` で GPU に知らせる。`SWAP` はそこで完了する
- `frame_crc` にフレーム番号を足し、`CRC_FRAME` (`0x0A`) で `FRAME_CRC` と同じフレームの番号が読める
- **3 通りの比較** (シナリオ `scenarios/*.json`、参照モデル [`gpu_model.py`](../tools/harness/gpu_model.py)):
  - Verilator: `make scenario SCENARIO=...` がシステム全体の RTL (GPU・調停・SDRAM コントローラ + SDRAM のモデル・表示・CRC) で走らせ、
    check ごとにモデルの CRC、RTL の `frame_crc`、出力した画像から Python で計算した CRC の 3 つを比べる
  - 実機: `harness.py scenario <file>` が同じシナリオを送り、`FRAME_CRC` (フレーム番号で「SWAP の 2 フレーム後」を確かめる) とキャプチャを比べる
  - 結果: `m5_basic` (端・はみ出し・幅 1・画面外・幅 0・SWAP の往復)、`m5_stress` (全画面の描画を続ける)、`m5_upload` (`UPLOAD`) の全 check で、
    モデル = Verilator = 実機。キャプチャは 99.7〜100%、`UNDERFLOW` 0
- **最悪ケース**: Verilator で表示のライン読み出しの待ち時間を数えると、描画が続いていても最大 351 クロック (5.6us)。締め切り 4000 クロックの 1/10 以下
- 速さ: 全画面の `CLEAR` が 0.84ms (実機、ホストの送信を含む)
- アップロードが遅かった (320x240 で 4.8 秒) のは RP2 のブリッジが原因で、1 文字ずつ `getchar` で読み、受信を 16 進で全部送り返していたため。
  ブリッジ v2 (まとめて読む + 生データで書く `spib`) で 0.9 秒になった (2KiB の書き込みが 62ms → 9.6ms)

### M5 の前に: SDRAM クロックの位相 ✅

M4 では SDRAM の読み出しが取り込み位置 5 の 1 点でしか通らず、配置配線が変わると落ちる心配があった。そこで:

- 2 つ目の rPLL で `clk_sys` (63MHz) を作り、同じ PLL の `CLKOUTP` (位相をずらした 63MHz) を ODDR で反転して SDRAM のクロックにした。
  位相 (`PSDA`、1/16 周期 = 約 1ns 刻み) は `MEM_CLK` (`0x15`) で実行時に変えられる。apicula は `DYN_DA_EN` (動的位相) に対応している
- **`DUTYDA` は立ち下がりの絶対位置**だった。8 に固定して `PSDA` だけ変えると立ち上がりしか動かず、ODDR で反転した SDRAM 側の立ち上がり
  (= `CLKOUTP` の立ち下がり) は動かない。位相 8, 9 では両方のエッジが重なってクロックが潰れる。RTL で `DUTYDA = PSDA + 8` にしている
- 位相 x 取り込み位置の BIST (`harness.py memtest --phases 0-15`)。8MiB 全域で:

  ```text
  phase  5 6        (# = 合格)
     11  . .        <- 6〜11 はコマンド・アドレスの保持時間が足りなくなる (SDRAM がコマンドの変わり目で取り込む)
     12  # .
     13  # .
     14  # .
     15  # #
      0  # #        <- 既定 (位相 0、取り込み位置 5)
      1  # #
      2  # #
      3  # #
      4  . #
  ```

- 既定のまま (位相 0、取り込み位置 5) で、前に 4 段・後ろに 3 段 (それぞれ約 4ns・3ns) の余裕がある。M4 の「5 だけ」は半周期刻みで見ていたため
- `harness.py selftest` が毎回この余裕を測って記録し、どちらかが 2 段を切ったら不合格にする

### M4 の結果 ✅

- 表示 ([`fb_scanout.sv`](../rtl/vdp/fb_scanout.sv)): ソースのライン n を表示しているあいだに、ライン n+1 を SDRAM から 160 ワードのバーストで読み、
  2 ライン分のライン バッファ (BSRAM 1 個) に置く。320x240 RGB565 を縦横 2 倍、8bit に広げて出す。`CONTROL` bit3 で切り替え
- 調停 ([`sdram_arb.sv`](../rtl/vdp/sdram_arb.sv)): 表示が優先、メモリテストとアップロードはその次
- SDRAM コントローラにバースト読み出し (同じ行で毎クロック READ、最後だけオートプリチャージ) を追加
- アップロード: `mem_test` のポート (`0x30`)。`spi_slave` は `0x30`〜`0x3F` でアドレスを進めないので、1 トランザクションで
  `MEM_ADDR` を書いてから 1 ライン (640 バイト) を流し込める
- 参照モデル ([`tools/harness/fbmodel.py`](../tools/harness/fbmodel.py)) が、アップロードした画像から実機の出力と CRC を作る
- 結果 (テスト画像: グラデーション・カラーバー・市松・線・円):
  - `FRAME_CRC` が参照モデルと完全一致 (`0xfb1c0e67`)。フレームバッファ 2 面ぶんの位置 (slot 0 と 256) の両方で
  - `UNDERFLOW` 0
  - キャプチャは境目以外で 99.7% 一致 (境目は 72%。斜めの線や円の縁が多い画像なので)
  - アップロードは 4.8 秒 (8MHz)。ほとんどが 1 ライン 1 回の USB の往復 (約 20ms x 240)。まとめて送るのは M5 の `UPLOAD` で
- **SDRAM の取り込み位置の訂正**: 最初は M3 の既定 (6) のままで、`FRAME_CRC` がフレームごとに変わった。
  取り込み位置ごとに見ると、5 だけが正しい CRC で安定 (4, 6 は揺れ、7 はいつも 1 ワード先を読む)。
  BIST もバースト (1 行 256 ワードずつ) で読むようにしたら、BIST でも 5 だけが合格するようになった (8MiB で 0.62 秒)
- ハーネスの落とし穴: `memtest` が取り込み位置を最後に試した値のまま残していた。今は終わったら元に戻す

### M2 の結果 ✅

- [`rtl/vdp/frame_crc.sv`](../rtl/vdp/frame_crc.sv): 表示ピクセルを R, G, B の順のバイト列とした標準の CRC-32 (`zlib.crc32` と同じ値)。
  VBLANK でラッチし、`FRAME_CRC` (`0x05`〜`0x08`) で読む。`0x05` を読んだ時点の値を残りの 3 バイト用に取っておくので、4 バイトが同じフレームの値になる
- `CONTROL` bit1 (アニメーション停止) でスプライトをリセット位置に止めると、毎フレーム同じ画面になる
- `make render FREEZE=1` が参照画像と、Python で計算した各フレームの CRC (`build/render_frozen/frames.json`) を出す
- 実機の `FRAME_CRC` = `0x82f897f9` が参照と完全に一致。止めないと毎フレーム変わる
- `harness.py frametest`: CRC の比較とキャプチャの比較を 1 回で行う (2 秒ほど)。違う参照を渡すと不合格になることも確認

### M3 (SDRAM) の結果 ✅

オープンソースのツールチェーンでパッケージ内 SDRAM が使えることを確かめました。BSRAM に切り替える代わりの案は不要になりました。

- apicula の [doc/sdram.md](https://github.com/YosysHQ/apicula/blob/master/doc/sdram.md) にある内部 I/O の名前 (`O_sdram_clk` = `IOR11B` など 55 本) を
  cst の `IO_LOC` にそのまま書けば、nextpnr-himbaechel が指定どおりに配置し、gowin_pack もビットストリームにできる
- コントローラ ([`sdram_ctrl.sv`](../rtl/vdp/sdram_ctrl.sv)): 63MHz、CL2、1 ワードずつ (オートプリチャージ付き)。SDRAM のクロックは逆相 (ODDR)
- 読み出しの取り込み位置を半周期単位で変えて BIST を回すと、実機では 5〜7 が合格、2〜4 が不合格 (データがまだ来ていない)。
  シミュレーションのモデル (4〜5 が合格) より 1 半周期ほど遅い。このときは既定を真ん中の 6 にした。
  **→ M4 で訂正**: 6, 7 が合格したのは 1 ワードずつ読んでいたから (SDRAM が出し終えたあとも浮いたバスが値を保つ)。
  次のワードがすぐ続くバーストでは 5 だけが正しく読める。BIST もバーストで読むように直し、既定を 5 にした (下の M4 の結果)。
  もっと余裕がほしくなったら rPLL の位相調整 (PSDA) で SDRAM のクロックをずらす
- 8MiB 全域の BIST (パターンとその反転を書いて読む、1 回 1.2 秒) が 10 回連続で合格。1 回が 64ms より十分長いので、リフレッシュも効いている
- `harness.py memtest` (取り込み位置ごとの BIST)、`harness.py mem read/write` (1 ワード)

### FPGA 側の構成

`rtl/vdp/` (ベンダ非依存) に置くもの: SPI スレーブ、レジスタ、コマンド FIFO、GPU コア (描画エンジン)、SDRAM コントローラ、
アービタ、ライン バッファ、CRC。`rtl/gowin/` には PLL・CLKDIV・DVI 出力と、SDRAM のクロック出力 (逆相) だけを置きます。

| クロックドメイン | 周波数 | 中身 |
| --- | --- | --- |
| `clk_sys` | 63MHz | SPI スレーブ (SCK をサンプリング)、レジスタ、GPU、SDRAM |
| `clk_pix` | 25.2MHz | 表示タイミング、ライン バッファの読み出し、CRC、DVI |

ドメイン間は、ライン バッファ (デュアルポート BSRAM) と「次のラインを読んで」のトグル同期だけにします。
`rtl/vdp/` に足したモジュールには、いつも通り `sim/tb_<名前>.sv` を書きます。

### GPU コマンド (初版の案)

コマンド FIFO にはレジスタ `CMD` (1 アドレス) へ連続で書き込みます。1 コマンドは 32bit ワードの並び。

| コマンド | 引数 | 段階 |
| --- | --- | --- |
| `CLEAR` | color | M5 |
| `FILL_RECT` | x, y, w, h, color | M5 |
| `SWAP` | — (次の VBLANK で表示面を切り替え、終わるまで後続を待たせる) | M5 |
| `CLIP` | x0, y0, x1, y1 | M6 |
| `POINT` / `DRAW_LINE` | x0, y0, (x1, y1,) color | M6 |
| `UPLOAD` | addr, len, data… | M5 (M4 ではレジスタのポートで代用) |
| `BLIT` | src_addr, src_stride, x, y, w, h, flags (透過・反転), key_color | M7 |
| `DRAW_TILEMAP` | map_addr, tile_addr, cols, rows, scroll_x, scroll_y | M8 |

## 進める順番

```text
M0 ブリッジ + ホストツール ─► M1 SPI + レジスタ ─► M2 CRC + キャプチャ比較 ─┐
                                                                          ├─► M4 表示 ─► M5 ─► M6 ─► M7 ─► M8 ─► M9
M3 SDRAM ✅ (オープンソースのツールで動いた) ──────────────────────────┘
```

M0〜M2 で「書き込み → 実行 → 確認」のループが回るようになれば、M4 以降はシナリオと参照モデルを足しながら機能を増やしていくだけになります。
